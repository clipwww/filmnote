# 影記 / filmnote — 產品規格

> 台灣在地的觀影紀錄 SaaS。
> 本規格由 2026-09-05 的資料來源調研（`docs/research/DATA_SOURCES.md`）與技術選型調研（`docs/research/STACK.md`）推導而來，兩份文件中的實測數據為本規格的事實基礎。

---

## Problem Statement

在台灣記錄自己看過的電影，目前沒有堪用的工具。

Letterboxd 是這個品類的國際標準，但對台灣使用者有三個結構性的缺陷：

1. **中文片名混亂。** Letterboxd 的 metadata 來自 TMDB，而 TMDB 的繁體中文標題實測只有 **84.4%** 與台灣官方核准片名一致，另有 **10.6%** 的片根本沒有中文標題。使用者搜尋《鬼媽媽的假期》會找不到，因為 TMDB 上它叫 `Our Season`。

2. **完全沒有「電影院」的概念。** Letterboxd 只記錄「你看了什麼」，不記錄「你在哪裡看的」。對台灣使用者而言，在信義威秀的 IMAX 廳看跟在家裡看是完全不同的體驗，但工具無法區分。

3. **無法記錄消費。** 票價、票數、影廳、播放版本（IMAX / 4DX / 3D）這些資訊，對想回顧「我今年在電影院花了多少錢、去了幾次、最常去哪家」的使用者完全不可得。

現有的替代方案是自己用 Google Sheet 或個人專案手工維護，但這無法分享、無法累積、且資料來源終將因人工維護而荒廢。

---

## Solution

一個以台灣為主場的觀影紀錄工具，讓使用者用最低摩擦記下每一次進電影院的經驗，並以視覺化的方式回顧自己的觀影軌跡。

核心價值主張，按重要性排序：

1. **記得住台灣的片名。** 以文化部影視及流行音樂產業局的「電影片分級及相關資訊」開放資料作為官方核准片名的校正層，蓋過 TMDB 不一致的中文標題。
2. **記得住你在哪看的。** 內建全台 107 家電影院、932 個影廳的官方主檔（影視局「全國電影院資料」），使用者從下拉選單挑選，不必打字。
3. **記得住你花了多少。** 票價、票數、影廳、版本皆可記錄，並以此產生消費統計。
4. **看得見自己的軌跡。** 貢獻圖、時段熱力圖、月度趨勢、影城分布 —— 把觀影行為量化成可回顧的圖像。

明確**不做**的事：不做社群動態牆、不做影評系統、不做評分排行、不做場次查詢。這些是 Letterboxd 與開眼電影網的主場，正面對打贏不了。

## User Stories

### 記錄一次觀影

1. As a 使用者, I want 用片名搜尋電影並選取, so that 我不必手動輸入片名與相關資訊。
2. As a 使用者, I want 搜尋時看到繁體中文片名與海報, so that 我能快速確認選到正確的片。
3. As a 使用者, I want 搜尋結果同時比對原文片名與中文片名, so that 我用任一種語言都找得到。
4. As a 使用者, I want 記錄時只需要填片名、日期、影城三個欄位, so that 我能在散場走出影廳的路上三十秒內記完。
5. As a 使用者, I want 日期預設為今天, so that 我最常見的情境（剛看完就記）不需要任何額外操作。
6. As a 使用者, I want 影城下拉選單記住我上次選的, so that 我常去同一家戲院時不必每次重選。
7. As a 使用者, I want 影城選單包含「串流平台」「影展」「家中」「其他」等非影城選項, so that 我在非戲院看的片也能記錄。
8. As a 使用者, I want 票價、票數、影廳、播放版本、備註都是選填, so that 我懶得填的時候不會被擋住。
9. As a 使用者, I want 國別與片長由系統自動帶入, so that 我不需要查也不需要填。
10. As a 使用者, I want 記錄同一部片多次（多刷）, so that 我能看出自己重複觀看的片。
11. As a 使用者, I want 編輯與刪除已建立的紀錄, so that 我填錯時能修正。
12. As a 使用者, I want 記錄一次可包含多張票, so that 我跟家人朋友一起看時能記錄實際花費。

### 找不到片的時候

13. As a 使用者, I want 搜尋不到片時看到「手動新增這部片」而不是錯誤訊息, so that 我不會卡住而放棄記錄。
14. As a 使用者, I want 手動新增作品時只需填片名與年份, so that 補資料的成本夠低我才願意做。
15. As a 使用者, I want 手動新增時可以選填上傳海報, so that 我的紀錄看起來不會空空的。
16. As a 使用者, I want 手動新增的作品立刻能用於記錄, so that 我不必等待審核。
17. As a 使用者, I want 我手動新增的作品在審核通過前只有我看得到, so that 我不必擔心自己填錯的資料影響到別人。
18. As a 使用者, I want 我新增的作品在事後比對到 TMDB 時自動補上海報與詳細資料, so that 我不必回頭手動維護。
19. As a 管理者, I want 審核使用者新增的作品後才進入公共片庫, so that 公共資料的品質不會因為開放而崩壞。
20. As a 管理者, I want 合併重複建立的作品, so that 同一部片不會在片庫中分裂成多筆。

### 瀏覽與分享

21. As a 使用者, I want 有一個公開的個人頁, so that 我能把我的觀影紀錄分享給朋友。
22. As a 使用者, I want 個人頁網址是好記的使用者名稱, so that 我唸得出來也貼得出去。
23. As a 使用者, I want 首次登入時系統自動幫我產生使用者名稱, so that 我不必在註冊時多做一步設定。
24. As a 使用者, I want 之後能修改我的使用者名稱, so that 我對自己的公開身分有控制權。
25. As a 使用者, I want 修改使用者名稱後舊網址仍能連到我, so that 我先前分享出去的連結不會失效。
26. As a 未登入的訪客, I want 直接瀏覽別人的公開個人頁, so that 我不必註冊就能看到朋友分享的內容。
27. As a 未登入的訪客, I want 瀏覽電影頁看到有哪些人看過這部片, so that 我能發現這個站的內容價值。
28. As a 使用者, I want 我的紀錄預設是公開的, so that 分享是預設行為而不需要額外設定。
29. As a 使用者, I want 我的票價預設不公開, so that 我的消費金額不會在我沒察覺的情況下被看到。
30. As a 使用者, I want 主動開啟票價公開, so that 我想參與消費統計時可以選擇加入。
31. As a 使用者, I want 把個別紀錄設為私密, so that 某些我不想公開的觀影經驗仍能被記錄。
32. As a 使用者, I want 分享連結時有正確的預覽圖與標題, so that 貼到社群或通訊軟體時看起來是完整的。
33. As a 搜尋引擎, I want 能索引公開的個人頁與電影頁, so that 這個站能被自然搜尋找到。

### 統計與視覺化

34. As a 使用者, I want 看到年度觀影次數的貢獻圖, so that 我能一眼看出自己這年的觀影密度與空窗期。
35. As a 使用者, I want 看到星期 × 時段的熱力圖, so that 我能發現自己習慣什麼時候看電影。
36. As a 使用者, I want 看到月度觀影趨勢折線圖, so that 我能看出自己的觀影頻率變化。
37. As a 使用者, I want 看到影城分布統計, so that 我知道自己最常去哪家戲院。
38. As a 使用者, I want 看到播放版本分布（IMAX / 3D / 數位）, so that 我知道自己偏好什麼樣的觀影規格。
39. As a 使用者, I want 看到國別分布, so that 我了解自己的觀影口味。
40. As a 使用者, I want 看到年度總花費、總場次、總票數, so that 我能回顧這一年在電影上的投入。
41. As a 使用者, I want 看到多刷排行, so that 我知道自己最愛哪部片。
42. As a 使用者, I want 所有統計都能按年份切換, so that 我能逐年回顧。
43. As a 使用者, I want 統計圖表在手機上也能正常閱讀, so that 我在通勤時也能看。

### 登入與帳號

44. As a 使用者, I want 用 Google 帳號登入, so that 我不必記另一組密碼。
45. As a 使用者, I want 登入後立刻能開始記錄, so that 我不必先完成一堆設定。
46. As a 使用者, I want 匯出我的所有紀錄, so that 我的資料不被鎖在這個服務裡。
47. As a 使用者, I want 刪除我的帳號與所有資料, so that 我對自己的資料有最終控制權。

### 資料品質與法遵

48. As a 使用者, I want 看到的中文片名是台灣官方核准的正式名稱, so that 我看到的片名跟我在戲院看到的一致。
49. As a 使用者, I want 回報片名或影城資訊有誤, so that 錯誤的資料能被修正。
50. As a 使用者, I want 回報某家影城已歇業或缺漏, so that 影城清單能保持正確。
51. As a 著作權人, I want 有明確的管道通知平台移除侵權內容, so that 我的權利能被保護。
52. As a 著作權人, I want 我的通知被受理後內容立即被移除, so that 侵權的損害能被停止。
53. As a 使用者, I want 我的內容被移除時收到通知並能提出回復通知, so that 誤判時我有申訴管道。
54. As a 平台經營者, I want 系統符合著作權法第六章之一的避風港要件, so that 平台不因使用者的侵權行為負擔賠償責任。
55. As a 平台經營者, I want 頁面標示政府開放資料的顯名聲明與 TMDB 的 attribution, so that 平台符合兩者的授權條款。

### 資料匯入

56. As a 既有使用者（David）, I want 匯入我在舊 log 專案累積的觀影紀錄, so that 我的歷史資料不會斷在遷移這一刻。
57. As a 使用者, I want 匯入時系統自動比對片名到片庫, so that 我不必逐筆手動對應。
58. As a 使用者, I want 看到匯入時哪些片沒比對到, so that 我能決定要不要手動處理。

## Implementation Decisions

### 技術棧

| 層 | 選擇 | 備註 |
|---|---|---|
| 框架 | **Nuxt 4** | 最新穩定版為 4.5.2；Nuxt 3 已 EOL，無 Nuxt 5 |
| 算繪 | **公開頁 SSR，登入後 SPA** | 逐路由混合模式。公開頁需 SEO 與 OG 預覽；登入後的儀表板大量使用圖表，SSR 無益 |
| UI | **Nuxt UI v4** | v4 已將原本付費的 Pro 元件全數併入 MIT 免費。Table 基於 TanStack Table v8 且內建虛擬捲動 |
| 樣式 | **Tailwind CSS 4** | Nuxt UI v4 的基底 |
| 圖表 | **ECharts（tree-shaken 模組化 import）** | 單一函式庫涵蓋全部圖表類型。`calendar` 座標系對應貢獻圖，`heatmap` series 對應時段矩陣 |
| Lint | **oxlint + `@antfu/eslint-config`** | oxlint 負責儲存時的即時回饋；ESLint 負責 commit/CI 的完整檢查（含 template 與 type-aware 規則）。以 `eslint-plugin-oxlint` 關閉重疊規則 |
| DB / Auth / Storage | **Supabase** | Postgres + Auth（Google provider）+ Storage + RLS 一包。以 `@nuxtjs/supabase` 整合 |
| 部署 | **Vercel Hobby** | 收費時升級 Pro |

**選型排除紀錄**（避免日後重複評估）：

- **oxlint 單獨使用**：不看 `<template>`、在 `.vue` 內停用 `no-unused-vars`、缺 `require-v-for-key` 等 essential 規則（46 條 `vue/*` vs `eslint-plugin-vue` 的 252 條，template a11y 零覆蓋）。Nuxt 官方曾試行後否決（PR nuxt/nuxt#32049）。
- **PrimeVue**：v5 已從 MIT 轉為閉源商業授權，需 license key。
- **`@sidebase/nuxt-auth`**：Nuxt 4 支援議題長期未解，依賴停滯。
- **`nuxt-auth-utils`**：本專案走 Supabase Auth 故不採用；若日後改用，須 pin `>=0.5.30`（低版本有 login CSRF 漏洞 GHSA-xc49-mgwh-9pjv）。

### 資料來源與分層

**這是本專案最關鍵的架構決策。** 三層各司其職：

| 層 | 職責 | 保存期限 |
|---|---|---|
| **TMDB**（主要入口） | 使用者搜尋的第一線；海報、簡介、演職員、國際 ID | **快取 ≤ 6 個月**（條款硬性要求），須排程刷新 |
| **政府開放資料**（校正層） | 110–113 年官方核准中文片名、國別、片長、級別；**全台影城主檔** | **可永久保存**（政府資料開放授權條款第 1 版） |
| **UGC**（補完層） | 補 TMDB 未涵蓋的約 20% 作品 | 永久，但受避風港取下程序約束 |

**主從關係的說明**：政府分級資料最新僅到 113 年（2024），存在一年以上落差；而使用者記錄的多為剛上映的新片。因此在最高頻的使用路徑上，**TMDB 是入口，政府資料是校正層**，而非反過來。

### 資料模型

**兩層作品模型（不可省略）**：同一部片會因國語版／日語版／2D／3D 分開核准（113 年實測 `中文片名` 有 56 組重複）。若以核准紀錄作為作品，統計會重複計數。

⚠️ **`分級證明字號` 不能作為主鍵**（2026-09-05 全量驗證推翻先前假設）。113 年的字號帶系列前綴（`局影外第113001號`），而 **110–112 年的 CSV 沒有前綴**，四個系列（局影外／本／港／陸）各自從 001 編號，因而大量撞號：

| 年度 | 字號重複筆數 |
|---|---|
| 110 | 128 |
| 111 | 143 |
| 112 | 157 |
| 113 | 0 |

前綴無法從國別可靠推回（實測以國別大類還原後，112 年仍有 30 組撞號）。**改用確定性複合鍵 `年度:字號:正規化片名`**，在 110–113 年全部 3,116 筆上實測唯一，且重跑匯入不會產生重複列。

```
film（作品）
├─ id           PK, 內部 UUID   ← 唯一 100% 存在的識別碼
├─ tmdb_id      UNIQUE, NULLABLE ★
├─ imdb_id      NULLABLE
├─ title_zh     ← 政府核准名優先，TMDB 次之
├─ title_orig
├─ country / runtime / release_year
├─ poster_source enum(tmdb | ugc | none)
├─ visibility   enum(public | private)   ← UGC 新增者預設 private
└─ source       enum(tmdb | gov | ugc)

certificate（核准紀錄）        ※ 多對一 → film
├─ id           PK ← 確定性複合鍵「年度:字號:正規化片名」
├─ permit_no    分級證明字號（**跨年度不唯一**，僅為屬性）
├─ film_id      FK
├─ year / rating / country / language / producer / runtime_raw
└─ version_note ← 自片名剝除的版本標註（中文版／數位修復版…）

cinema（電影院）
├─ tax_id       PK ← 統一編號（實測 107/107 有值、零重複）
├─ name         ← 事業名稱（對外營業名稱）
├─ company_name ← 公司名稱（登記法人全銜）
├─ hall_count / address / phone
├─ lat / lng    ← 一次性地理編碼補入
├─ city         ← 正規化後的縣市
└─ kind         enum(cinema | streaming | festival | home | other)

user
├─ id           PK ← Supabase auth.users
├─ username     UNIQUE ← email 前綴為預設值，可修改
└─ show_cost    bool, default false

username_history  ← 供改名後的 301 轉向
├─ old_username PK
└─ user_id      FK

viewing_record（觀影紀錄）
├─ id / user_id / film_id / cinema_id
├─ watched_at   ← 日期時間
├─ cost / tickets / hall / version / memo   ← 全部選填
└─ visibility   enum(public | private), default public
```

★ **`tmdb_id` 必須可為 NULL。** 實測 20% 的台灣上映片在 TMDB 找不到；若設為必填或主鍵，這些片永遠無法入庫，且事後極難補救。

**片庫規模（110–113 年，由正式匯入管線實際產出，非估計）**：

| 項目 | 筆數 |
|---|---|
| 核准紀錄（`certificate`） | 3,116 |
| **`film` 實際筆數** | **2,669** |
| ├ 命中 TMDB | 2,401（90.0%） |
| └ 未命中，`tmdb_id` 為 NULL | 268 |
| **跨年度／跨版本重複而收斂掉** | **447（14.3%）** |
| 來源資料有缺陷的核准紀錄 | 12 |

資料完整性已驗證：`film.id` 與 `certificate.id` 皆唯一；3,116 張證明書**全部恰好歸屬一次**，零重複歸屬、零遺漏。

→ 若以 `permit_no` 作為作品主鍵，片庫將虛胖 **14.3%**（且該欄位本身在 110–112 年並不唯一），所有「看了幾部片」的統計皆會失真。兩層模型不是潔癖，是正確性要求。收斂最極端的案例是《TAYLOR SWIFT | THE ERAS TOUR》，**一部片有 13 張證明書**。

→ **268 部作品的 `tmdb_id` 為 NULL**，佔片庫 10.0%。這些片只能存在於自己的庫中，坐實了「`tmdb_id` 必須可為空」不是理論考量。未命中的型態包含：國家劇院現場放映（NT Live）、動漫劇場版、日本小眾片、以及政府資料把兩部片寫在同一列的情況（如《屁屁偵探：咖哩香料事件》《屁屁偵探：瓢蟲遺跡之謎》）。

### TMDB 比對演算法

政府資料與 TMDB 的對照不是單純的片名比對。以下為實測驗證有效的版本（在 805 筆母體上命中 89.4%、端到端可用 80.0%）：

```
① 雙查詢：以「原文片名」與「中文片名」分別查詢 TMDB search（language=zh-TW），候選取聯集
② 正規化：NFKC → 剝除版本標註 → 去標點空白
     版本標註 =（中文版|國語版|日文版|數位修復版|4K|經典重映|加長版|前篇|後篇|IMAX版…）
     實測 113 年有 60 筆（7.5%）片名內嵌此類標註，不剝除必然誤配
③ 評分：原文精確 +5 ／ 中文精確 +5 ／ 中文前綴 +3 ／ 上映年落在 ±1 年 +1.5
     年份「只加分、不懲罰」
④ 片長交叉驗證：將「映演時間」（1 時 45 分 30 秒）解析為分鐘；
     若與 TMDB runtime 差 > 5 分且無片名精確吻合 → 判定誤配，退回未命中
⑤ 總分 < 3 → 標記 unmatched，進 UGC 佇列（不硬猜）
```

**三個已驗證的失敗模式，實作時必須避開**：

1. **年份不可作硬篩。** 重映片的核准年 ≠ TMDB 上映年（《紅豬》核准 113 年、TMDB 1992；《千禧曼波》核准 113 年、TMDB 2001）。以 `year` 參數硬篩會誤殺全部重映與數位修復片。
2. **TMDB 的 `original_title` 常為母語而非英文。** 政府給 `Porco Rosso`，TMDB 存 `紅の豚`；政府給 `Ponyo on the Cliff by the Sea`，TMDB 存 `崖の上のポニョ`。單靠原文片名對不上。
3. **缺少片長驗證會產生假陽性。** 未加驗證的版本將《一屍到底》配到 `Making Of One Cut of the Dead`、《貓的報恩》配到 `Batman Returns`。

### 政府資料匯入管線

**取得方式**（非標準，需多解析一層）：

- 入口為 `bamid.gov.tw/OpenData.aspx?SN=<代碼>`，回傳「包裝 JSON」而非資料本身
- 真正的逐年 CSV 連結藏在該 JSON 的 `相關檔案` 欄位，格式為 `名稱(URL);名稱(URL);...` 的字串，需自行切分
- 該 JSON 的 `FileName` 欄位是陷阱：只指向**最舊**的年度
- 包裝 JSON 與 CSV **皆為 UTF-8 with BOM**，直接 `JSON.parse` 會失敗，須先去除 BOM

**防禦性解析**（實測遭遇的源頭資料損毀）：

| 問題 | 實測量（113 年 / 2025 年） | 處理 |
|---|---|---|
| 原文片名被 Excel 誤判為日期（《福田村事件》= `Sep-23`） | 1/805 | 偵測日期樣式 → 改用中文片名查詢 |
| 原文片名編碼損毀（全問號） | 1/805 | 偵測 → 改用中文片名查詢 |
| 原文片名拼寫錯誤（`INVISILBLE`、`GRIME STORY`） | ≥2/805 | 無法自動修，落入 UGC 佇列 |
| **CSV 引號損壞導致欄位右移** | 2/3,116 | 《劇場版IDOLiSH7》原文片名含逗號未被引號包住，使國別變成片名片段。**必須以陣列模式解析並偵測欄數**，用 `columns: true` 會靜默錯位 |
| **映演時間放的不是片長** | 8/3,116 | 見過發行商名稱（《大發明家》=`木棉花國際股份有限公司`）與上映日期區間（《戀戀風塵》=`113.08.17-113.08.17`） |
| 事業名稱前後空白 | 2/107 | 一律 trim |
| 縣市「台/臺」混用 | 影城 CSV | 正規化 |
| 廳數為字串 | 影城 CSV | 轉數字（實測總和 932，與影視局統計月報吻合） |

**匯入管線必須可中斷、可續跑。** 全量匯入實測為 3,116 筆核准紀錄、9,076 次 TMDB 請求、耗時 3,872 秒。這種長度的工作隨時可能中斷，必須記錄每筆的處理狀態並在重啟時跳過已完成者。

⚠️ **關於節流的更正**：先前根據 Python 原型的批次間速度差（709 筆/259 秒 vs 868 筆/1,669 秒）推論「免費 key 會累積節流」，**該推論未經證實**——正式匯入的 9,076 次請求中，重試 0 次、遭 429 節流 0 次。惟該次執行的實際併發接近 1，**高併發下的節流行為仍未驗證**。重試與指數退避因此屬防禦性設計；提高併發時應觀察 `TmdbClient.stats.throttled`。

**匯入範圍**：分級資料匯入 **110–113 年**（schema 已統一為 9 欄的年份，約 3,000 筆）。104–109 年 schema 不同（中文與外文片名合併於同欄），暫不匯入。影城資料只取 **2025 年**單一年度（跨年度 schema 不穩定，不應合併）。

### 影城維護策略

一次性建檔 + 年度校正 + UGC 回報。全台僅 107 家，`統一編號` 為天然主鍵。每年排程抓取最新 CSV 後 diff 出新增／消失的影城，經人工確認後更新。影廳層級資訊（IMAX / 4DX / 座位數）政府資料不提供，完全依賴 UGC。

**明確排除 Google Places API 作為建檔來源**：其條款明文禁止「複製並儲存商家名稱、地址」，禁止用於「名錄或目錄型服務」，且經緯度僅能快取 30 天。經緯度改以一次性地理編碼取得（107 筆在任何服務的免費額度內）。

### 海報與圖片

| 情境 | 處理 | 理由 |
|---|---|---|
| 有 TMDB 的作品（約 80%） | **熱連結 `image.tmdb.org`，不自行轉存** | 風險最低（未重製、未散布）、零儲存與頻寬成本、避開 6 個月快取條款 |
| UGC 新增的作品（約 20%） | 使用者選填上傳，存於 Supabase Storage，長邊限制 500px | 缺海報時以片名文字卡片呈現，不影響核心功能 |
| 已比對到 TMDB 的作品 | **禁止上傳海報** | 無必要，只增加曝險 |

**關鍵認知**：TMDB 的付費訂閱買到的是「合法存取 API 的權利」，**不是「合法使用海報的權利」**。電影海報的著作權屬片商，TMDB 自身亦不擁有（其官方論壇自承 "if a photographer disagreed with his/her image being used here we would have to take it down"），因此無法轉授權。

### 法遵要件（Phase 1 必須完成，事後無法回溯適用）

著作權法第 90 條之 7 給予資訊儲存服務提供者免責，但適用前提在第 90 條之 4，且**必須在侵權發生時已經建置**：

1. 服務條款中告知使用者著作權保護措施，並確實履行
2. 告知「三次涉有侵權情事應終止全部或部分服務」（三振條款）
3. 公告接收侵權通知的聯繫窗口（如 `copyright@`）
4. 實作通知／取下／回復通知流程（回復通知：著作權人 10 個工作日內未提訴訟證明者，須於 14 個工作日內回復）

**海報顯示不得置於付費牆之後。** 第 90 條之 7 第 2 款要求「未直接自使用者之侵權行為獲有財產上利益」，而訂閱制 SaaS 將侵權內容鎖於付費牆後是否構成該款，台灣尚無明確實務見解。付費功能應鎖在統計分析、匯出等與海報無關的價值上。

**Attribution 義務**：

- 政府資料開放授權條款第 1 版要求顯名標示，且「未盡顯名標示義務者，**視為自始未取得授權**」
- TMDB 要求顯示其 logo 並標示 "This product uses the TMDB API but is not endorsed or certified by TMDB"，且 TMDB logo 須less prominent than 本站標誌

### 營運約束

- **TMDB 使用免費 developer key**（本階段不營利）。一旦收費或放置廣告，須升級至商業訂閱（約 $149/月）。
- **Vercel Hobby 禁止商業使用**，且其定義涵蓋「宣傳未來要收費的產品」「接受捐款」。在 Hobby 期間不得於站上宣傳未來收費或開啟贊助管道。收費時同步升級 Vercel Pro。
- **Supabase 免費專案閒置 7 天會自動暫停。** 上線前須以排程 ping 維持活躍；上線後公開頁的 SSR 流量即足以避免。

## Testing Decisions

### 什麼是好的測試

只測外部行為，不測實作細節。測試應該在重構內部結構時保持通過，只在使用者可觀察的行為改變時失敗。不測 composable 的內部狀態、不測元件的內部方法、不對 Supabase client 做 mock 後斷言呼叫參數。

### 接縫（seams）

刻意只設兩個接縫。

**接縫 A — 比對與正規化（純函式）**

這是本專案最容易出錯、也最值得測試的部分，且**已有現成的黃金資料**：113 年全部 805 筆政府分級資料與其實際比對結果。

測試對象：

- TMDB 比對器：給定一筆政府紀錄與一組 TMDB 候選 → 正確的配對結果或 `unmatched` 判定
- 片名正規化：NFKC、版本標註剝除、標點與全半形處理
- `映演時間` 字串 → 分鐘數的解析
- 防禦性解析：Excel 日期誤判、編碼損毀、拼寫錯誤的處理路徑
- 影城資料正規化：trim、縣市台/臺、廳數轉型

**必測的回歸案例**（皆為實測發現的真實失敗）：

| 案例 | 期望行為 |
|---|---|
| 《紅豬》核准 113 年、TMDB 1992 | 命中，不因年份差距被拒 |
| 《千禧曼波》核准 113 年、TMDB 2001 | 命中 |
| 政府給 `Porco Rosso`、TMDB `original_title` 為 `紅の豚` | 透過中文片名查詢命中 |
| 《一屍到底》 | **不得**配到 `Making Of One Cut of the Dead`（片長驗證攔截） |
| 《貓的報恩》 | **不得**配到 `Batman Returns` |
| 《福田村事件》原文片名為 `Sep-23` | 走中文片名路徑，不因日期字串而崩潰 |
| 《SPY x FAMILY CODE: White》3 張證明書 | 收斂為 1 部 `film`、3 筆 `certificate` |
| 片名含 `(中文版)`、`數位修復版` | 剝除後比對 |

比對器對 TMDB 的呼叫以錄製的 fixture 回應，不打真實 API —— 測試必須離線且可重複。

**接縫 B — HTTP 層（Nitro `/api/*`）**

其餘全部經此接縫，對真實測試資料庫（Supabase 本機或測試專案）發出 HTTP 請求並斷言回應。

測試對象：

- 觀影紀錄的建立、修改、刪除
- **可見性規則**：未登入者看得到公開紀錄、看不到私密紀錄；`show_cost` 為 false 時票價不出現在回應中
- UGC 建立作品：建立後只有作者可見；審核通過後進入公共片庫
- 使用者名稱：唯一性、保留字、改名後舊名的 301 轉向
- 影城查詢與非影城選項
- 匯出與帳號刪除

**不設第三個接縫。** 不寫元件層測試；UI 行為若需驗證，以少量端對端測試涵蓋關鍵路徑（登入 → 記錄一次觀影 → 出現在個人頁），而非逐元件測試。

### Prior art

本專案為全新 repo，無既有測試可循。舊 `log` 專案亦無測試。因此接縫 A 的第一批測試將同時作為後續測試的風格基準：純函式、表格驅動、fixture 存於版本控制、無 mock。

## Out of Scope

**場次資料（showtimes）。** 明確排除，且非暫緩而是不做。理由：無任何國際供應商能公開確認覆蓋台灣（MovieGlu 與 International Showtimes 皆不公開國家清單，Gracenote 僅美加）；本地院線中僅秀泰技術友善，威秀有 Akamai 防護；場次爬蟲是每日皆可能損壞的東西，正是「人工維護終將荒廢」的具體形態。且 Letterboxd 本身亦無此功能 —— 記錄「看過什麼」是回顧行為，不需要場次。

**票房資料。** 已排除於產品範圍外。其 API（`boxofficetw.tfai.org.tw`）有 Cloudflare 防護且實測回傳 403。副作用是 2024 年後的新片失去政府資料來源，完全倚賴 TMDB 與 UGC。

**社群功能。** 追蹤、動態牆、影評、評分、留言皆不在本階段。Letterboxd 的護城河為社群網路效應與多年累積的影評內容，正面競爭無勝算。

**棒球觀賽紀錄與小米手環資料。** 留在既有的 `log` 專案。棒球的資料來源問題完全未經研究，中華職棒無公開 API，是另一個獨立題目。

**104–109 年的分級資料。** 該區間 CSV schema 不同（中文與外文片名合併於同一欄、分級證明字號格式三變），需年度別清洗邏輯，暫不匯入。

**多語系介面。** 本階段僅繁體中文。

**行動 App。** 響應式網頁即可。

## Further Notes

### 覆蓋率的期望管理

實測數據（母體為影視局 **110–113 年全部 3,116 筆**核准電影片，即本專案的完整匯入範圍）：

| 年度 | 筆數 | 命中率 | 中文標題 | 與政府相符 | 海報 | 台灣上映日 | 端到端可用 |
|---|---|---|---|---|---|---|---|
| 110 (2021) | 709 | 89.0% | 90.5% | 84.3% | 98.9% | 42.6% | 80.4% |
| 111 (2022) | 734 | 88.8% | 90.2% | 82.7% | 98.8% | 51.8% | 79.7% |
| 112 (2023) | 868 | 93.5% | 89.9% | 81.5% | 98.8% | 72.2% | 83.9% |
| 113 (2024) | 805 | 89.4% | 89.4% | 84.4% | 99.3% | 71.4% | 80.0% |
| **合計** | **3,116** | **90.3%** | **90.0%** | **83.2%** | **98.9%** | **60.6%** | **81.1%** |

**覆蓋率跨年度穩定。** 命中率在 88.8–93.5% 之間，端到端可用率在 79.7–83.9% 之間。約 80% 的可用率是結構性事實，而非單一年度的偶然。

**唯一有顯著年度落差的是「台灣上映日」**（42.6% → 71.4%）—— TMDB 的台灣區域資料近兩年才補齊。此欄位不影響核心功能（使用者記錄的是自己的觀看日期），但涉及上映日的衍生分析在 2021–2022 年區間會有約半數缺值。

依國別拆解顯示缺口**不在歐洲而在日韓**：美國 98.4% 命中、法國與英國各 94.4%、泰國 95.8%；但日本僅 78.6%、韓國僅 77.6%。

缺口的三種型態：日本劇場版／總集篇／OVA（銀魂劇場版、刀劍亂舞、劇場版 OVERLORD、屁屁偵探）、演唱會與偶像影像作品（JUNG KOOK、RM、嵐 5x20、hololive）、台港中的獨立片與數位修復重映（戀戀風塵、恐怖份子、蘇州河 4K、家有囍事 4K）。

**20% 不是失敗指標，是設計 UGC 的依據。** 且缺口的分布對本產品有利 —— 動漫愛好者與影展觀眾正是最願意主動補充資料的族群。因此「找不到這部片」必須是一等公民的使用流程，而非錯誤狀態。

- ~~**早期年度（104–112）的比對覆蓋率未測。**~~ → ✅ **110–112 年已實測**（見下方覆蓋率表），命中率與 113 年無顯著差異，「預先匯入 110–113 年」的決策維持不變。**104–109 年仍未測**，但該區間 schema 不同且已列為 Out of Scope。
- **TMDB 演職員（cast / crew）的中文化程度未測。** 已測項目僅涵蓋片名與簡介。
- **付費牆與著作權法第 90 條之 7 第 2 款的關係需律師意見。** 無法從條文推斷。
