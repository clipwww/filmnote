## 0. 設計論點

### 主要物件不是海報，是票根

Letterboxd 是海報導向的，因為它每部片都有海報。我們有 10% 沒有（268/2669 部 `tmdb_id` 為 NULL），而且我們真正比它多的東西——**官方核准片名、影城、廳別、版本、票價、場次時間**——正好是一張台灣電影票根上印的東西。

所以：**紀錄的預設呈現是票根式的欄位卡，海報是選配的鑲嵌**。

這一個決定同時解掉三件事：

1. 海報缺席不再是降級。沒海報的作品不是「破圖的海報卡」，它就是一張票根，跟有海報的那張一樣完整。
2. 我們的差異化資訊（影城、廳別、票價）獲得版面主權，而不是擠在海報底下的小字。
3. 我們不會長得像 Letterboxd。

Letterboxd 自己的無海報處理是 `#1F282F` 灰盒中央塞 9–18px 的小字（實測其 `main-CoHtwXNO.css` 的 `--poster-no-image-background`）；Airtable 官方建議把沒圖的**濾掉**。這是我們可以打贏的地方——不是因為技術，而是因為我們手上有官方核准片名，文字卡承載的資訊本來就比海報多。

**驗收標準：無海報的卡片要好到使用者不會希望它變成海報。**

### 資料是墨，不是彩虹

實測 David 的 169 筆紀錄：有觀影的 165 天當中，**161 天是 1 場、4 天是 2 場，沒有任何一天 ≥3 場**（`fixture.stats.dailyAll`）。

這推翻了「照抄 GitHub 五階綠色」的預設做法——五階裡有三階永遠不會被畫出來。日層級的資料實際上是**二元的**。

因此年度出席圖**不是熱力圖，是出席圖**：沒去／去了／去了兩場。第三階留給雙片連映（David 的備註裡真的有「4DX連映馬拉松場(下)」），讓那些日子自己跳出來。

而全站的序列色階一律**單色相明度階（紙 → 墨）**。理由有三，每一個都是硬的：

- ECharts 的 heatmap **不支援 decal**（色盲用的紋理），單色相明度階是唯一可存取的序列色方案。
- 分級章五色（普 #5CB731、護 #00A2ED、輔12 #FFD300、輔15 #D66800、限 #E30009）**亮度非單調**——實算 0.364 → 0.320 → 0.678 → 0.242 → 0.164。它是類別色，不是序列色，不能當色階用。
- 墨階讀起來像印刷密度，跟票根／單據的敘事一致。而且它把彩色完全讓給互動，讓「一個視圖一個重點色」這條紀律真的守得住。

### 避開的東西，以及為什麼

實測 Letterboxd 線上 CSS（2026-09-04 `main-CoHtwXNO.css`, 1.1 MB）後確認，以下四項**同時**是 AI 生成設計的預設**和** Letterboxd 的簽名，屬雙重危險，全部放棄：

| 手法 | Letterboxd 實證 | 我們的替代 |
|---|---|---|
| 近黑底 + 單一螢光重點色 | `--theme-background-color:#14181C` + `#00E054` | 暖褐暗底（`#1D1610`）+ 墨階資料 + 低彩度琥珀 |
| ALL-CAPS + 追蹤字距眉標 | `letter-spacing:.075em` 用於全部微標籤 | 中文本來沒有大小寫；用中文小標配量詞 |
| 中點分隔 meta 串（`A · B · C`） | CSS `content:'·' / '•' / '—'` | 開眼式括號量詞串：`林口威秀 (7廳) 2D 16:00 2張` |
| 等寬字型當資料微標籤 | `--font-stack-pitch-sans` | Inter 的 `tnum` 表格數字 |

另外兩項：

- **藍灰中性軸**。Letterboxd 全部中性色落在 hue≈210 的同一條軸上（`#334455`→`#DDEEFF`，3-digit 縮寫用了約 1,100 次），全站沒有一個真正的中性灰。這是它最不被察覺卻最具識別性的資產。我們的中性色必須離開那條軸——改放**暖 kraft 軸（HSL 色相 25–40）**，而且 chroma 是看得見的（見 §1.0：這是「收藏冊」調性的主要載體）。
- **秀泰官網已整套採用 shadcn/Tailwind 預設**（`--primary: oklch(40.1% .146 301.28)` = `#572D88`）。在台灣，「做成圓角 SaaS 卡片」等於長得像影城訂票網站。圓角一律 ≤4px。

不用漸層。不用發光。不在按鈕文字後面加「→」。

## 1. 色彩

> **2026-09-06 調性變更**：David 拍板把整體調性從前一版的「冷結構 + 暖火花」
> 改成**「更重的溫暖收藏感」**（前任交接筆記 §3 標記為待決的那一項）。
> 本章整章已重算。**§1.6 是落地的唯一真值**，所有色值以 hex 為準（OKLCH 只是設計時的座標）。

### 1.0 調性：收藏冊，不是儀表板

前一版的立場是「版面是資料化的紀律，暖色只是一點火花」。新的立場是：
**這個產品是一本票根簿，不是一個儀表板。**

三個具體的位移：

1. **中性軸從「幾乎沒有顏色的暖白」變成「看得出來是紙」。**
   亮底 chroma 從 0.004 拉到 0.025（**6 倍**），暗底從 0.006 拉到 0.016。
   紙色不再是「白裡帶一點暖」，而是真的一張米色的台紙。

2. **頁面底與卡片面互換角色。** 前一版是「頁面最亮、卡片次亮」（＝儀表板的預設）。
   新版是**頁面＝冊頁台紙（`paper-50`，較深較暖）、卡片＝票根紙（`paper-25`，較亮）**。
   票根實際地「貼」在冊頁上。深度由**面的色階**表達，不加陰影
   （§3 的「陰影預設 none」不變，這一版反而更需要它——有了兩層紙就不需要投影）。
   暗色同構：頁面 `paper-950`、卡片 `paper-900`。

3. **琥珀從「單一火花」放寬到「可以承載表面」。**

**被取代的規則**：舊 §1.2 的「**一個視圖只用一次重點色**」作廢。

**取代它的規則**：

> **琥珀可以塗在「介面」上，永遠不可以塗在「資料」上。**

也就是說：選取態、目前年份、今天、主要動作、頁籤、票根卡的日期帶、區塊眉標的細線——
這些是介面狀態，琥珀想出現幾次都可以。
但**圖表裡任何一個編碼資料的標記都不准是琥珀**，序列一律走墨階（§1.3）。

這個換法是安全的，因為當初真正在保護的東西是「**顏色不編碼資料**」，
而不是「顏色只准出現一次」。前者是可存取性（§1.3 三條硬理由），後者只是節制的手段。
節制現在改由 **chroma 紀律**執行：中性軸 chroma ≤ 0.031，琥珀表面 chroma ≥ 0.062，
中間那段沒有東西——所以「暖」與「重點」在視網膜上仍然是兩件事，不會糊成一片奶油色。

**沒有跟著改的東西**（這些是可存取性與識別性的結構決定，不是風格偏好）：
序列色階仍是單色相明度階、圓角仍 ≤4px、中性軸仍遠離 hue≈210、
不用漸層／發光／按鈕後綴「→」、中文仍不用 webfont、`tabular-nums` 仍由 Inter 供應、
主要物件仍是票根不是海報。

### 1.1 中性軸：台紙與票根

暖 kraft 軸。HSL 色相落在 **25–40**（前一版是 45，與琥珀同軸；現在刻意讓中性偏褐、
琥珀偏金，兩者拉開約 10–18°），離 Letterboxd 的 hue≈210 有 170° 以上。
色相從亮端 82 緩降到暗端 58（OKLCH），亮處是米色紙、暗處是木頭與皮革，不是灰。

```
                                          用途（Nuxt UI 對應）
--color-paper-25   #FDF9F1   票根紙        --ui-bg：卡片／彈窗／下拉／輸入框
--color-paper-50   #F8EDDC   冊頁台紙      body 底、--ui-bg-muted
--color-paper-100  #EADDCA   凹陷面        --ui-bg-elevated、墨階零格
--color-paper-200  #DACCB9   分隔／邊框    --ui-bg-accented、--ui-border
--color-paper-300  #C5B5A3   邊框（強）    --ui-border-accented
--color-paper-400  #948777   佔位／停用    --ui-text-dimmed（亮）／--ui-text-muted（暗）
--color-paper-500  #776A5D   輔助文字      --ui-text-muted（亮）／--ui-text-dimmed（暗）
--color-paper-600  #5F5348   次文字        --ui-text-toned（亮）
--color-paper-700  #4A4036   內文          --ui-text（亮）／--ui-bg-accented（暗）
--color-paper-800  #3D332C   —            --ui-bg-elevated（暗）、--ui-border（暗）
--color-paper-900  #29211A   主文字／暗卡  --ui-text-highlighted（亮）／--ui-bg（暗）
--color-paper-950  #1D1610   暗頁底        body 底（暗）
```

**一條軸兩個模式。** 這 12 階同時供應亮色的文字與暗色的面，反之亦然
（Nuxt UI 的 `--ui-text-*` / `--ui-bg-*` 全部從同一組 neutral 派生，見 §1.6）。
所以每一階都必須**在兩個方向上都可讀**——下表每一格都實算過：

| 角色 | 亮色（對票根紙 `#FDF9F1`） | 亮色（對台紙 `#F8EDDC`） | 暗色（對暗卡 `#29211A`） | 暗色（對暗頁 `#1D1610`） |
|---|---|---|---|---|
| `900` / `50` 主文字 | **15.07:1** | 13.67:1 | **13.67:1** | 15.44:1 |
| `700` / `200` 內文 | **9.62:1** | 8.73:1 | **10.04:1** | 11.34:1 |
| `600` / `300` 次文字 | **7.10:1** | 6.44:1 | **7.92:1** | 8.95:1 |
| `500` / `400` 輔助 | **4.99:1** | 4.53:1 | **4.52:1** | 5.10:1 |
| `400` / `500` 佔位／停用 | **3.34:1** | 3.03:1 | **3.02:1** | 3.41:1 |

⚠️ **`400` 與 `500` 這兩階是整條軸最緊的地方**，因為它們必須同時當亮色的淡字與暗色的淡字。
上表最小值 3.02:1，只剩 0.02 的餘裕。**不要「順手微調」這兩階**，動它們會在另一個模式裡破線。

**面的分層**（不是文字，不適用 4.5:1，要的是「看得出是兩張紙」）：

| | 對比 | |
|---|---|---|
| 台紙 `50` ↔ 票根紙 `25` | 1.10:1 | 票根浮在冊頁上 |
| 凹陷面 `100` ↔ 票根紙 `25` | 1.27:1 | 輸入框、hover、骨架 |
| 邊框 `200` ↔ 票根紙 `25` | 1.50:1 | 1px 髮絲線 |
| 暗頁 `950` ↔ 暗卡 `900` | 1.13:1 | |
| 暗 `800` ↔ 暗卡 `900` | 1.29:1 | |

### 1.2 重點色：琥珀（現在承載表面）

HSL 色相 **43.6–46.7**，維持前一版的定位——離陶土色（hue 15）與 Letterboxd 橘（hue 30）
各 15° 以上。**這個距離是刻意的，不要在實作時「微調」回去。**

```
--color-amber-50   #FFF1C2   ← 亮色選取／今天／本年的底
--color-amber-100  #F9E4A4   ← 亮色 hover／較強的染色面
--color-amber-200  #F0D481
--color-amber-300  #DFBC4F
--color-amber-400  #C9A62B   ← 暗色的文字／邊框／實心鈕底（與前一版同值）
--color-amber-500  #A8850E
--color-amber-600  #866500   ← 亮色的文字／邊框／實心鈕底
--color-amber-700  #6F5101
--color-amber-800  #573E03
--color-amber-900  #422D04   ← 暗色 hover
--color-amber-950  #2D1D02   ← 暗色選取／今天／本年的底
```

已驗算的配對：

| 用法 | 亮色 | 暗色 |
|---|---|---|
| 實心按鈕 | `amber-600` 底 + `paper-25` 字 → **5.16:1** | `amber-400` 底 + `paper-900` 字 → **6.76:1** |
| 連結／邊框／focus ring（在卡片上） | `amber-600` → **5.16:1** | `amber-400` → **6.76:1** |
| 連結／focus ring（在頁面台紙上） | `amber-600` → **4.68:1** | `amber-400` → **7.64:1** |
| focus ring（在凹陷面 `100`/`800` 上） | `amber-600` → **4.05:1** | `amber-400` → **5.25:1** |
| 選取態底色 | `amber-50` | `amber-950` |
| 選取態底色上的文字 | `paper-900` → **14.03:1** | `paper-50` → **14.08:1** |

⚠️ **暖中性軸 + 琥珀 = 兩者會互相靠近，這是這個調性最大的技術風險。**
在冷灰底上「一塊淡黃 = 被選取」是白送的；在米色台紙上不是。所以加一條硬規則：

> **任何琥珀染色面對它所在的中性面，OKLab ΔE 必須 ≥ 0.030。**

實算（全數通過）：

| 染色面 vs 中性面 | ΔE |
|---|---|
| `amber-50` vs 票根紙 `paper-25` | 0.057 |
| `amber-50` vs 台紙 `paper-50` | **0.039** ← 最緊的一組 |
| `amber-100` vs `paper-100` | 0.060 |
| `amber-200` vs `paper-200` | 0.082 |
| `amber-950` vs 暗卡 `paper-900` | **0.033** ← 次緊 |
| `amber-900` vs 暗 `paper-800` | 0.047 |

最緊的兩組只有 0.033–0.039。**因此「選取」不准只靠染色**：
選取態一律是**染色面 + 2px `amber-600`/`amber-400` 的起始邊**（左邊或下緣，視元件而定）。
這同時滿足 WCAG 1.4.1（顏色不是唯一的區辨手段），也讓票根卡的選取看起來像被夾了一張書籤。

### 1.3 序列色階：墨階（圖表專用）

7 階，亮度單調（已驗算）。**這一條是可存取性的硬需求，沒有因為調性改變而放寬**：
ECharts heatmap 不支援 decal，單色相明度階是唯一可存取的序列色方案；
而分級章五色亮度非單調（0.364→0.320→0.678→0.242→0.164），是類別色不是序列色，不能當色階用。

墨階跟著中性軸一起變暖（色相 61–74，與 `paper` 同一條暖軸），但**它不是琥珀**——
chroma 上限 0.035，遠低於琥珀表面的 0.062 下限。資料永遠是墨，不是重點色。

```
亮色（零格 = paper-100，不屬於色階）
--heat-0 #EADDCA  1 #CEC4B7  2 #B1A392  3 #91816F  4 #685946  5 #413525  6 #1A1209
 相對亮度 0.7347    0.5602     0.3762     0.2287     0.1053     0.0380     0.0067   ✅ 單調遞減

暗色（整條反轉，紙色在高值端）
--heat-0 #392F24  1 #4C3E30  2 #685949  3 #857565  4 #A59788  5 #CEC4B9  6 #F6F1EB
 相對亮度 0.0303    0.0520     0.1057     0.1865     0.3191     0.5610     0.8850   ✅ 單調遞增
```

零格對卡面：亮 1.27:1、暗 1.21:1，**看得出來是一個格子，但明確是「空的」**。

⚠️ **圖表必須放在卡片（`bg-default` 票根紙）上，不要直接放在裸台紙（`body`）上。**
零格對背景的對比在兩種紙上不一樣，而且亮暗不對稱（實算）：

| | 放在卡片上 | 放在裸台紙上 |
|---|---|---|
| 亮色 | **1.27:1** ✅ | 1.16:1 ⚠️ |
| 暗色 | **1.21:1** ✅ | 1.37:1 |

亮色放在裸台紙上是最弱的一格——零格會開始跟頁面底糊在一起，整張圖看起來「少了一層」。
這是台紙變暖之後才出現的新限制，前一版的頁面底是最亮的紙所以不會發生。

⚠️ **少於 7 階時，要在色階上「拉開取值」，不要取相鄰階。**
這條規則是前任實作 mockup 時量出來的（第一版把 0/1/2 對到 `heat-0/2/4`，
暗色模式下「沒去」與「1 場」對比只有 1.64:1，整張年表幾乎看不見）。
新色階重算後結論相同：

| 對應方式 | 亮 0↔4 | 暗 0↔4 |
|---|---|---|
| 相鄰階 `0 / 2 / 4` | 1.84:1 ❌ | 1.94:1 ❌ |
| **拉開 `0 / 4 / 6`** | **5.05:1** ✅ | **4.60:1** ✅ |

WCAG 1.4.11 對「承載意義的圖形物件」要求 3:1。最重要的區分（有去／沒去）兩個模式都過。

⚠️ **誠實記一筆：次要區分（1 場 ↔ 2 場，即 `heat-4` ↔ `heat-6`）在新色階下是
亮 2.74:1 / 暗 2.53:1，暗色比前一版的 2.78:1 退步了 0.25。**
原因是暖化後暗頁底變亮（相對亮度 0.0043 → 0.0060），零格必須跟著抬高才看得見，
整條暗階的動態範圍被壓縮。這是調性換來的代價，不是失誤。

**但這一版不接受它，改用非顏色的手段補掉**：
`≥2 場`的日子在 `calendar` 座標系上**另外疊一個 `scatter` 系列畫一個小點**
（ECharts 的 `calendar` 支援 `coordinateSystem: 'calendar'` 的 scatter）。
實測資料只有 4 天會被畫到（165 天中 161 天 1 場、4 天 2 場、0 天 ≥3 場）。
這樣「雙片連映」不再依賴 2.53:1 的明度差，反而比前一版更穩。

同一條規則適用於分布長條圖：**條的填色不要用色階淺端**。
若標籤要壓在條上，就把標籤移到條的上方一行，讓填色可以自由加深。

### 1.4 分級章：類別色，不是色階

文化部影視局官方分級章顏色（49×49px 實際取樣）。**只在作品頁與作品詳情使用**，
不進搜尋結果、不進列表。

| 級別 | 底色 | 章內文字色 | 對比 |
|---|---|---|---|
| 普遍級 | `#5CB731` | `paper-950` | 7.04:1 |
| 保護級 | `#00A2ED` | `paper-950` | 6.29:1 |
| 輔12 | `#FFD300` | `paper-950` | 12.41:1 |
| 輔15 | `#D66800` | `paper-950` | **4.97:1** |
| 限制級 | `#E30009` | `#FFFFFF` | 4.92:1 |

⚠️ **章內文字色逐級不同，而且這一版換成了 `paper-950`（`#1D1610`），不是 `paper-900`。**
理由是輔15 `#D66800` 配 `paper-900` 只有 **4.40:1，不及格**；換到 `paper-950` 才是 4.97:1。
白字在 普／護／輔12 上全部不及格（2.54 / 2.84 / 1.44），只有限制級能用白字。
**這是全站唯一一處刻意不用 `--ui-text-highlighted` 的地方**，因為那個 token 是 `paper-900`。

形式是**實色方塊 + 級別字**，旁邊的說明文字用 `paper-900`——這正是真實分級章的樣子，
而且色彩只當標記、不當文字，可存取性由結構保證而非靠運氣。

### 1.5 語意色

沿用 Nuxt UI 的別名，但把 `neutral` 換成暖 kraft 軸：

- `primary` → amber
- `neutral` → 上面的 paper 暖階
- `error` `success` `warning` `info` → 沿用 Nuxt UI 預設，僅用於表單驗證與 toast，**不進資料視覺化**

⚠️ `warning` 的 Nuxt UI 預設就是 Tailwind 的 amber。在暖底上它會跟 `primary` 撞。
表單警告請用 `error`（紅）或改用文案，**不要在同一個畫面上同時出現 `primary` 與 `warning`**。

### 1.6 落地：Nuxt UI v4 的 token 覆寫

> **這一節是給 frontend session 的交付物。以下內容可以直接落地，數值皆已驗算。**
> 對照版本：`@nuxt/ui@4.11.0`（實檔 `node_modules/@nuxt/ui/dist/runtime/index.css`
> 與 `dist/runtime/plugins/colors.js`，2026-09-06 實讀）。

#### 為什麼不能只改 `app.config.ts`

實讀 `index.css` 的 `@layer theme`，Nuxt UI 有**五個** token 硬寫死 `#fff`、
**一個**派生錯階，全部不從 neutral／primary 派生：

| token | 模式 | 硬寫死的值 | 漏在哪裡 |
|---|---|---|---|
| `--ui-bg` | 亮 | `#fff` | 頁面與**所有卡片、彈窗、下拉、輸入框**的底 |
| `--ui-text-inverted` | 亮 | `#fff` | 實心按鈕、badge、alert 的字 |
| `--ui-text-highlighted` | 暗 | `#fff` | 暗色的主文字 |
| `--ui-bg-inverted` | 暗 | `#fff` | **`UCalendar` 選取日、`UButton neutral solid`、`UTabs` 作用中頁籤、`UTimeline`、`UStepper`、`UPageCard`** |
| `--ui-border-inverted` | 暗 | `#fff` | **`UCheckbox` / `URadioGroup` 的邊框、`UInputMenu` / `UTextarea` 的 ring** |

⚠️ **後兩個是前任沒抓到的。** 實測 `.nuxt/ui/*.ts` 主題檔，`bg-inverted` 出現在
`calendar.ts`（9 處）、`button.ts`（5）、`timeline.ts`（5）、`tabs.ts`（4）、
`stepper.ts`（3）、`page-card.ts`（3）；`border-inverted` 出現在 `radio-group.ts`（6）、
`checkbox.ts`（5）。**`UInputDate` 內部就是 `UCalendar`**，所以這條直接踩在新增紀錄的主流程上——
暗色模式下「你選的那一天」會是一塊純白。

第六個問題，**派生錯階**（不是硬寫死，但更難查）：

實讀 `dist/runtime/plugins/colors.js:16`，`--ui-primary` 是
`--ui-color-primary-500`（亮）／`--ui-color-primary-400`（暗），**亮色是 500 不是 600**。
本文 §1.2 的所有亮色琥珀對比都是以 600 算的。若不覆寫，實際跑出來是：

| | 實際（500 `#A8850E`） | 應該（600 `#866500`） |
|---|---|---|
| 琥珀文字／連結 on 票根紙 | **3.16:1 ❌** | 5.16:1 ✅ |
| 實心鈕：紙色字 on 琥珀底 | **3.27:1 ❌** | 5.16:1 ✅ |

**這是純文字對比不及格，而且畫面上看起來「就是有點淡」，不會有任何錯誤訊息。**

第七個，**圓角**：`index.css` 的 `--ui-radius:0.25rem`（4px），
而 Tailwind 的 `rounded-md` = 1.5×、`rounded-lg` = 2×。實測 `.nuxt/ui/*.ts`
用到 `rounded-md` **59 次**、`rounded-lg` **26 次**、`rounded-xl` 1 次——
也就是預設狀態下全站元件是 **6px 與 8px 圓角**，直接違反「圓角 ≤4px」的硬約束
（§0：秀泰官網已整套採用 shadcn/Tailwind 預設，圓角 SaaS 卡片在台灣＝影城訂票網站）。
把 `--ui-radius` 設成 `0.125rem`（2px）之後：`sm`=2px、`md`=3px、`lg`=4px、`xl`=6px，
只剩 `page-cta.ts` 那一處 `rounded-xl` 是 6px（可接受，或由該元件單獨覆寫）。

## 2. 字體排印

### 2.1 決策：中文不用 webfont

這是本專案最違反直覺、但證據最硬的一個決定。

實測（以本專案自己的 `.data/films.json` 為語料）：

| 方案 | 首屏成本 | 問題 |
|---|---|---|
| Google Fonts 送 Noto Sans TC 單字重 | 首屏 20 片 / **675 KB** | 全套 105 片共 2.14 MB |
| Google Fonts 雙字重 | 首屏 **1,272 KB** | 要第二個字重會**靜默切成 variable**，等於把 100–900 全吃下來 |
| 自架 static 子集（全站 3,141 字） | 單一請求 **≈393 KB** | **UGC 會破字** ← 致命 |
| **平台系統字型** | **0 KB** | 需明確寫出各平台家族名 |

自架子集看起來最漂亮，但實測 David 一人的 169 筆紀錄就用到 599 個不重複字元，其中 **30 個不在 films.json + venues.json 的 3,120 字全站字彙內**——含 `🎉`、`斎`（心斎橋）、`猗窩座`、`儸`、`殞`。這些字正好落在**備註**與**找不到的片名**，也就是硬約束 (1) 與整個情感內容區。子集化會讓它們變成豆腐格。

**所以：中文由平台字型供應，拉丁與數字由 Inter 供應。**

這不是妥協，是決定。PingFang TC、微軟正黑體、Noto Sans CJK TC 都是好字，產品因此在每個平台上看起來都像原生的。省下的 675 KB 直接變成首屏速度。

### 2.2 字型堆疊

```css
--font-sans: 'Inter', 'PingFang TC', 'Noto Sans CJK TC', 'Noto Sans TC',
             'Microsoft JhengHei', 'Source Han Sans TC', sans-serif;
```

三件事必須理解，否則會出現簡體或日文字形：

1. **Inter 排第一是刻意的。** Inter 沒有漢字，所以中文自動落到下一個；但數字與拉丁字母由 Inter 供應，`tabular-nums` 與 `slashed-zero` 才會真的生效——**Noto Sans TC 完全沒有 `tnum`／`pnum`／`lnum`**（實測其 GSUB 只有 aalt ccmp dlig fwid hist hwid liga locl pwid ruby vert vrt2），`tabular-nums` 掛在它身上是空操作。
2. **必須寫出語言專屬家族名。** macOS 上蘋方是三個獨立家族（蘋方-繁 / 蘋方-簡 / 蘋方-港），寫 `"PingFang TC"` 才保證繁體字形。Windows 上若只寫 `sans-serif`，Chromium 在缺語言提示時**一律用簡體字型**（Chromium issue 41188235）。
3. **`nuxt.config.ts` 已有 `htmlAttrs: { lang: 'zh-Hant-TW' }`**，語言提示這一半到位了。缺的只有 CSS 端的家族名。

Inter 與 Noto Sans TC 的視覺尺寸幾乎完全吻合（x-height 0.546 vs 0.543 em、cap-height 0.728 vs 0.733 em，差距 <1%），**不需要 `size-adjust`**。

Inter 走 `@nuxt/fonts`（0.14.0 已隨 `@nuxt/ui` 安裝並自動註冊），只取 Latin 子集。

### 2.3 原文片名要有自己的堆疊

實測 `.data/films.json` 全部 2,669 筆：**344 部（12.9%）的原文片名有字元是 Noto Sans TC 畫不出來的**，共缺 583 字——諺文 312、日本新字體 69、印度系 60、泰文 51、阿拉伯文 37、希伯來文 12。相對地中文片名只有 5 部（0.19%）缺字。

也就是說「中文片名／原文片名」並排的那一行，**每八筆就有一筆會出現字型不一致**。

處理方式是把它變成刻意的層級差，而不是 bug：

```css
.title-original {
  font-family: 'Inter', 'PingFang TC', 'Hiragino Sans', 'Noto Sans JP',
               'Apple SD Gothic Neo', 'Noto Sans KR', 'Noto Sans Thai', sans-serif;
  font-size: 0.8125rem;      /* 13px，明顯小於中文片名 */
  color: var(--color-paper-500);   /* 暗色模式用 paper-400 */
}
```

小一級、淡一階，讀者看到的是「附註」而不是「破面」。

### 2.4 度量

| 用途 | 字級 | 行高 | 說明 |
|---|---|---|---|
| 數字英雄（年份、場次） | 48–72px | 1.0 | Inter，`tabular-nums` |
| 頁面標題 | 28px | 1.35 | |
| 區塊標題 | 20px | 1.4 | |
| 片名（卡片） | 16px | 1.45 | |
| 內文 | 16px | **1.75** | 中文需要比拉丁更鬆 |
| 欄位標籤／輔助 | 13px | 1.5 | |
| 微標籤 | 12px | 1.5 | 不用 ALL-CAPS，不用等寬 |

⚠️ **行高一律寫死無單位值，絕不用 `line-height: normal`。** Noto Sans TC 的 hhea 預設行框是 **1.448 em**（asc 1160 / desc −288），Inter 只有 **1.21 em**，且兩者的 OS/2 typo 值又都是 1.000 em 與 hhea 不一致。用 `normal` 會讓同一段落的中英文行框不同，且跨瀏覽器不一致。

**行長**：中文內文 `max-width: 34ch`（≈560px）。不要沿用拉丁設計的 65ch——實算 66 個拉丁字元（Inter 加權平均推進 0.478 em）≈ **31.5 em ≈ 32 個漢字**，寫 65ch 等於一行 65 個漢字，資訊密度爆炸。

### 2.5 中文排版細則

```css
:root {
  line-break: strict;        /* 避免「。、」跑到行首。2020-07 起全瀏覽器可用 */
}
h1, h2, .title-zh {
  font-feature-settings: 'palt' 1;   /* 大標的標點收緊 */
  word-break: auto-phrase;           /* Chrome 119+，漸進增強 */
  text-wrap: balance;                /* Chromium 限 6 行、Firefox 10 行 */
}
```

四條規矩：

1. **絕不動 `letter-spacing`。** baseline-ui 的規則對 CJK 更嚴格——負字距會破壞漢字的 1 em 字身框。要收緊改用 `font-feature-settings: "palt" 1`（Noto Sans TC 的 GPOS 確實有 `palt`／`halt`）。
2. **不要用 `text-wrap: pretty` 解中文標題的孤字。** Firefox 完全不支援（Chrome 130 / Safari 26 才有），且 Chrome 官方說明文完全沒提到 CJK。打底靠 `line-break: strict`。
3. **UI 上不顯示《》。** `《》` 在中文字型裡是 1.000 em 全形，跟漢字同寬，片名頭尾各吃掉一個字寬，在緊湊卡片標題特別明顯。資料層保留，顯示層用字重與顏色區分片名。`text-spacing-trim` 只有 Chrome 123+ 支援，不能依賴。
4. **不要在 HTML 裡手打空格做中英間距。** `text-autospace` 初始值就是 `normal`，Chrome 140 / Safari 18.4 / Firefox 145 起是瀏覽器預設行為。量測欄寬時要預留這個浮動（新舊瀏覽器寬度會不同）。

### 2.6 品牌字

**「影記」二字以 inline SVG 路徑輸出**，不依賴任何字型。兩個字，畫一次，零位元組，且在任何平台上長得一模一樣——這是全站唯一保證一致的字型表現。


⚠️ **光是寫下這四個值沒有用。** Nuxt UI 的 `--ui-radius` 預設 `0.25rem`，
而它的元件主題實際用的是 `rounded-md`（1.5× = 6px，實測 59 處）與 `rounded-lg`（2× = 8px，26 處）。
不改 `--ui-radius` 的話，全站元件就是 6–8px 圓角，這條約束等於沒寫。
**`--ui-radius: 0.125rem` 已放進 §1.6 的 `main.css`**，之後 `md`=3px、`lg`=4px。

**陰影**：預設 `none`。層級用**邊框與底色**表達，不用投影。唯二例外是 overlay（`UModal` / `UPopover` / `UDrawer`），用 Tailwind 預設 `shadow-lg`。

這一版更不需要陰影了：**票根紙（`--ui-bg`）與冊頁台紙（`body`）本身就是兩層紙**（§1.1），
深度已經由色階給出。在那之上再加投影會同時毀掉「紙」與「不像 SaaS 卡片」兩件事。

分隔線 1px `paper-200`（亮）／`paper-800`（暗）。

**海報格幾何**（品類慣例，直接沿用）：比例 `2/3`，欄寬離散為 `70 / 110 / 150 / 230px`，gap `8px`。

### 4.3 TicketCard — 主要物件

一張紀錄的標準呈現。左邊窄帶是日期（票根的撕線位置，但**不畫齒孔、不畫虛線**——結構取自票根，材質不取）。

```
┌────┬──────────────────────────────────────────┬──────┐
│ 7  │ 劇場版 吉伊卡哇 人魚島的秘密              │      │
│ 26 │ ちいかわ 　　　　　　　　  ← 原文，小一級  │ 海報 │
│ 六 │ 林口威秀 (7廳) 2D 16:00 2張 NT$520        │ 選配 │
└────┴──────────────────────────────────────────┴──────┘
```

規則：

- **沒有海報時，海報欄不存在**，卡片自然變寬。不留灰色佔位，不畫破圖圖示。
- meta 行用**開眼式括號量詞串**（`(7廳)`、`2張`），不用中點分隔。
- 票價是 meta 行**最後一項**。被隱藏時它就是不存在，行變短——**絕不渲染 `NT$ ———` 之類的佔位**，那等於公告「這裡有一個價格」。
- `NT$0` 的 16 筆是免費／兌換票，顯示為 **「免費」/「兌換」**，不是 `NT$0`、也不是空白。這必須與「已隱藏」在視覺上不同。
- **日期帶染琥珀**（`amber-50` / `amber-950`），不是中性面。這是 §1.0「琥珀承載表面」在主要物件上的落點：票根的撕線位置整條變成重點色，卡片一眼就讀成票根而不是列表列。
  文字對比已驗：日期數字 `text-highlighted` **14.03:1 / 14.08:1**、星期 `text-muted` **4.65:1 / 4.65:1**。
- 日期帶的數字用 Inter `tabular-nums`。

網格模式下同一份資料轉成 2:3 直式：有海報就是海報，沒海報就是**票根卡**——片名設大、國別年份片長排成欄位。兩者是兩種正當的物件，不是一種的降級版。

### 4.4 數字不做成 stat tile

「大數字 + 小標籤 + 一排補充數據 + 漸層」是儀表板的預設長相，也正是要避開的東西。

我們把年度數字排成**一行有量詞的句子**，放在圖表下面當圖說：

```
2026 年看了 24 場、41 張票，花了 NT$9,860
```

數字用 Inter `tabular-nums` 放大到 1.5 倍字級並用 `text-highlighted`，量詞與連接詞維持內文字級與 `text-muted`。**圖是主角，數字是圖說**——這對得上「看得見自己的軌跡」，也避開了 stat tile 的版面。

## 5. 資料視覺化

ECharts 6.1.0 + vue-echarts 8.2.0（皆已安裝，不需新增套件）。

### 5.1 四張圖

| 圖 | 座標系 | 用途 |
|---|---|---|
| **年表 YearStrip** | 自製 SVG／CSS grid | 每年一列 × 53 週。全站簽名，兼任年份選擇器 |
| **年度出席圖** | `calendar` + `heatmap` | 選定年份的 7×53 日格 |
| **時段熱點圖** | `cartesian2d` + `heatmap` | 星期（7 欄）× 時段（縱向），**沿用舊專案的直式方向** |
| **月度趨勢** | `line` | 12 點，可疊多年 |
| **分布（影城／版本／國別）** | 橫式 `bar` | **不用圓餅圖** |

### 5.2 為什麼不用圓餅圖

實測 David 的分布極度傾斜：影城 林口威秀 115/169（**68%**）、國別 日本 98 / 美國 66 / 其餘 5 筆、版本 2D 126 / 4DX 20 / IMAX 7。一個佔 68% 的扇形不傳達任何東西。

而且 375px 下圓餅圖每個標籤只分到約 90px，`林口MITSUI OUTLET PARK威秀影城` 這種長度會被截到無法辨識。

**橫式長條 + `label` 置於 `insideTopLeft` + `width` 給滿容器寬**，實測 375px 下五個長片名全數完整顯示。長尾收成「其他 N 家」。

影城分布另外用一句話開頭，因為那才是真正的洞察：

> 你的主場是**林口威秀**，68% 的場次在這裡。

### 5.3 ECharts 硬限制（違反會靜默壞掉）

以下每一條都是實測，不是文件推測：

1. **絕不把 CSS 變數丟給 ECharts。** zrender 的顏色解析器不支援 `oklch()` / `color-mix()` / `var()`，而 Nuxt UI 4 的 token 正是 oklch。連續型 visualMap 會印 `"'var(--c-lo)' is an illegal color, fallback to '#000000'"` 並真的渲染成黑色。**在 JS 端先解析成 hex 再傳入**——所以本文的圖表色階全部以 hex 定義，不進 oklch token 系統。
2. **日曆的格子間距沒有專屬選項**，由 `calendar.itemStyle.borderWidth` 控制（`borderColor` 設成卡片底色）。要 2–3px 縫隙就設 `borderWidth: 3`。
3. **日曆只能設 `left` 與 `top`。** 同時設 `right` / `width` 會覆蓋 `cellSize` 的寬度分量，格子靜默變形成 6.9×14 的長條。這是最容易踩且錯了不會報錯的雷。
4. **`cellSize: 'auto'` 不是手機的解答**——寬高各自拉滿容器，375×180 下方格變成 6.90×23.40 的長條，直接破壞方格語彙。
5. **整年日曆固定 53 欄 × 7 列，總寬 = 53 × cellSize。** `cellSize:14` → 742px、`11` → 583px。**ECharts 自己完全不提供橫向捲動**，375px 手機上只會裁切。手機唯一乾淨解是固定像素寬（720–780px）放進外層 `overflow-x: auto`，並預先捲到最右（最近一週），兩側加漸層遮罩與捲動提示。
6. **`cartesian2d` heatmap 完全不畫空格**（實測 3 筆資料的 7×6 格盤只產生 5 個 path）。時段熱點圖必須把 7×N 全格補上 `value: 0`，否則「從未」的格子直接消失、露出卡片底色，看起來像破洞。`calendar` 則相反，會自動替區間內每天畫底色格。
7. **`cartesian2d` heatmap 兩軸都必須 `type:'category'` 且 `boundaryGap: true`**，違反會在 dev build 直接 throw。時段軸必須是字串桶，不能用 value 軸做連續小時。`visualMap` 是必需元件（可 `show:false`）。
8. **NaN / null 整格跳過。** 「零次」餵 `0`，「無資料」才留空。
9. **`visualMap.pieces` 用 `gt` / `lte`，不要用 `min` / `max`。** ⚠️ 2026-09-06 實測到的新坑：
   寫 `{ min: 6, max: 7 }` 接 `{ min: 8 }`，**值剛好等於 8 的那一格會靜默不畫**，
   露出底紙看起來像渲染破洞；值 9 反而正常。原因是 ECharts 把 pieces 當**連續區間**處理，
   `(7, 8)` 這一段沒有任何 piece 認領，邊界值就掉進縫裡。
   `gt` / `lte` 是明確的開閉界，區間首尾相接不留縫，邊界值不會無主。
   **這個錯 console 零錯誤、只有一格不見**，在 112 格的熱點圖上很容易被當成資料就是空的。
   實例：`docs/design/mockups/dashboard.html` 的週五 22:00 共 8 場，整格消失（已修）。
   同樣的寫法也在出席圖的三階上——`{ min:1, max:1 }` 接 `{ min:2 }` 會讓「剛好 2 場」的日子消失，
   而那 4 天正是雙片連映，是那張圖唯一想讓人看見的東西。
10. 深淺色切換用 ECharts 6 的 `instance.setTheme()`（vue-echarts 8 的 `:theme` prop 已接上），**不需要 dispose 重建**——網路上大量 v5 教學的結論在此不適用。但 `visualMap.pieces` 與明確的 `itemStyle.color` 不受 theme 影響，必須另外重算 option。

### 5.4 出席圖的分段

取值是 `heat-0 / heat-4 / heat-6`（**拉開**，不是相鄰階，理由見 §1.3）：

```js
// 亮色。⚠️ 用 gt/lte 不用 min/max，理由見 §5.3-9（用 min/max 會讓「剛好 2 場」整格消失）
visualMap: {
  type: 'piecewise', show: false,
  pieces: [
    { value: 0,        color: '#EADDCA' },  // 沒去（heat-0，中性，不屬於色階）
    { gt: 0, lte: 1,   color: '#685946' },  // 去了（heat-4）
    { gt: 1,           color: '#1A1209' },  // 兩場以上（heat-6，雙片連映）
  ],
}
// 暗色：'#392F24' / '#A59788' / '#F6F1EB'
```

只有三階，因為資料只支援三階（161 天 1 場、4 天 2 場、0 天 ≥3 場）。**不要為了「以後可能會有」而預留永遠不會被畫出來的色階。**

⚠️ **「1 場 ↔ 2 場」只有亮 2.74:1 / 暗 2.53:1，低於 WCAG 1.4.11 的 3:1。**
所以 `≥2 場`的日子**額外疊一個 scatter 系列畫一個小點**，不要只靠色差：

```js
{ type: 'scatter', coordinateSystem: 'calendar', symbolSize: 4,
  itemStyle: { color: '#FDF9F1' },   // 暗色用 '#29211A'
  data: daysWithTwoOrMore }          // 實測只有 4 天
```

點的顏色是**該模式的票根紙色**（壓在最深的 `heat-6` 上，亮 17.63:1／暗 14.09:1），
所以「雙片連映」變成一個看得見的記號，而不是一階分不太出來的灰。
這同時滿足 WCAG 1.4.1（顏色不是唯一的區辨手段）。

#### 週起始日：**週一**（`--week-start: 1`）

`calendar.dayLabel.firstDay: 1`，`nameMap: 'ZH'`。舊專案是「因為 dayjs 的 zh-tw locale 沒定義 weekStart 而退回 0」——新版要**顯式寫出來**，否則哪天有人改了 locale，整張圖會無聲位移。**兩張圖（年度出席圖與時段熱點圖）必須一致。**

前任把這一條留給 David 取捨。**這是純設計判斷、成本一行，所以由設計端決定，不佔用 David 的時間。** 選週一的理由：

1. **這兩張圖不是日曆，是回顧物。** 沒有人在上面挑日期或安排行程——點一格是「看那天看了什麼」。日曆慣例買到的熟悉感，在一個不拿來導航的物件上幾乎沒有價值。
2. **週日起始會把產品最強的洞察拆成兩半。** David 的資料顯示週五六日晚間是絕對熱區；週日起始讓 `日` 在頭、`五 六` 在尾，週末被切到色帶的兩端。週一起始讓 `五 六 日` 相鄰成一個看得見的區塊，而且時段熱點圖（星期在橫軸 7 欄）會自然讀成「一週往週末堆上去」。
3. **週解析度的分桶跟著變乾淨。** 年表 YearStrip 是按週收成的（§5.1），週一起始 = ISO 8601 週，年界的分桶不必自己發明規則。

**代價，寫清楚**：台灣的實體月曆與 Google Calendar 的 zh-TW 預設都是週日起始，所以列標籤第一格是 `一` 而不是 `日`，對一部分使用者會有一瞬間的不協調。緩解：列標籤用中文 `一二三四五六日`（本來就是），並在 `五六日` 三格用較重的字重讓週末成組。

**若 David 想翻回去**：`--week-start: 0` + 兩張圖的 `firstDay: 0`，就這樣。這個 token 存在的意義就是讓這個決定隨時可以推翻。

### 5.4b 圖表色的對帳表（給 frontend 逐項核對）

> `BaseChart` 至今還沒帶真實資料 render 過。這一節寫成**可以拿去對帳**的形式：
> 左邊是你該送進 ECharts 的值，右邊是渲染出來應該長什麼樣。
> **對不上時，這張表就是判斷「是我的 option 錯了還是色票錯了」的依據。**

#### 一、你要在 JS 端保存的常數（不要進 CSS 變數）

§5.3-1：zrender 不解析 `oklch()` / `var()` / `color-mix()`，而 Nuxt UI 4 的 token 正是 oklch。
所以圖表色**全部是 hex，在 JS 端保存**。這不是疏漏，是刻意的，不要「順手統一」進 token 系統。

```ts
export const CHART = {
  light: {
    bg:    '#F8EDDC',   // 冊頁台紙（body）——圖表不畫在這上面

    sunken:'#EADDCA',   // splitLine
    line:  '#C5B5A3',   // tooltip 邊框
    text0: '#29211A', text1: '#4A4036', text2: '#776A5D', text3: '#948777',
    accent:'#866500',   // 只用於「今天／本年／選取」這類 UI 狀態，永遠不編碼資料
    heat:  ['#EADDCA','#CEC4B7','#B1A392','#91816F','#685946','#413525','#1A1209'],
    att:   ['#EADDCA','#685946','#1A1209'],   // = heat[0] / heat[4] / heat[6]
  },
  dark: {
    bg:    '#1D1610',
    sheet: '#29211A',
    sunken:'#3D332C',
    line:  '#4A4036',
    text0: '#F8EDDC', text1: '#DACCB9', text2: '#948777', text3: '#776A5D',
    accent:'#C9A62B',
    heat:  ['#392F24','#4C3E30','#685949','#857565','#A59788','#CEC4B9','#F6F1EB'],
    att:   ['#392F24','#A59788','#F6F1EB'],
  },
} as const
```

⚠️ **`att` 必須恆等於 `heat[0] / heat[4] / heat[6]`。** 圖例的色塊與圖上的格子如果由兩份常數各自維護，
遲早會分岔——舊版 mockup 的 CSS `--att-1` 是 `heat-2`、JS 是 `heat-4`，圖例跟圖已經不同色了。
**只留一份，圖例從同一個陣列取。**

#### 三、三個一定要親眼看、算不出來的

1. **整張圖有沒有「破洞」。** 一格沒畫出來會露出 `sheet`，跟「零格」很像但更亮。
   `cartesian2d` heatmap 不畫空格（§5.3-6），而 `visualMap.pieces` 的邊界值也會靜默漏掉（§5.3-9）。
   **驗法**：把 `<details>` 的資料表跟圖並排，數字有值的格子在圖上都要有顏色。
   實測 `dashboard.html` 的 7×16 熱點圖，兩個坑各吃掉一格。
2. **零格對紙面的對比。** 亮色圖表若放在 `body` 台紙上只有 **1.16:1**（放票根紙上是 1.27:1），
   零格會開始跟頁面底糊在一起，整張圖看起來「少了一層」。暗色反而相反（台紙上 1.37、紙面上 1.21）。
   **所以圖表一律放在 `bg-default` 的面上**。
3. **暗色有沒有純白漏出來。** ECharts 的預設 `textStyle.color` 是 `#333`，tooltip 預設底是 `#fff`。
   **每一個都要顯式覆寫**，`baseTooltip()` 要帶 `backgroundColor: sheet`、`borderColor: line`、
   `textStyle.color: text0`、`extraCssText: 'box-shadow:none;'`（§3：陰影預設 none）。

#### 四、已知會對不上的地方（不是你的錯）

- **暗色「1 場 ↔ 2 場」只有 2.53:1**（亮色 2.74:1），低於 WCAG 1.4.11 的 3:1。
  這是暖化暗底換來的代價，已在 §1.3 量化，補救是那個 scatter 小點。**不要為了拉這個數字去改色階。**
- **`instance.setTheme()` 不會重算 `visualMap.pieces` 與顯式的 `itemStyle.color`**（§5.3-10）。
  切換深淺色時這兩者必須自己重算 option，只換 theme 會看到一半舊色。

### 5.5 從舊專案繼承什麼

舊 `../log` 是「兩套技術、一套配色」：貢獻圖與熱點圖是手寫 D3 v7 直接操作 SVG，折線／長條／圓餅是 Chart.js 4.5.1。

**繼承**：

- **格子節距** 15px 方塊 + 2px 間距（節距 17）。15px 對手指剛好，是觸控友善的尺寸，保留。
- **時段熱點圖的直式方向**（星期在橫軸 7 欄、小時在縱軸）。這在手機上比常見的橫式 7×24 合理得多——7 欄天生塞得進 375px，永遠不需要橫向捲動。這是舊碼裡最有價值的判斷。
- **「點格子 → 從底部滑出當日／當時段片單」的互動語彙**，含 90% 高度的 bottom sheet。這是這個產品最有價值的互動，原樣保留（改用 `UDrawer direction="bottom"`）。
- **標題字串格式**：`2024/03/15 (週五)`、`週三 14:00~15:00`。

**丟掉**：

- **GitHub 2013 的綠色階** `#eee → #d6e685 → #8cc665 → #44a340 → #1e6823`（熱點圖再往下接 `#18541c / #134016 / #0d2d0f`）。改用墨階。後三階深綠在暗底上幾乎會消失，整條無法支援深色模式。
- **白色 2px 描邊當格線**。在任何非白底（卡片底、深色模式）會變成刺眼白格線。改用真正的 gap。
- **硬編碼的 930×150 SVG 尺寸**。改由「欄數 × 節距 + padding」算出。
- **月份標籤用 4.333 週/月近似值定位**，會逐月漂移。改成對齊該月第一天所在欄。
- **`.attr('title', …)`**——那是加在 `<rect>` 上的 HTML title *屬性*，SVG 需要的是 `<title>` 子元素，所以舊站的貢獻圖**其實沒有任何 tooltip**。
- **d3 與 Chart.js 兩套 runtime**。新站統一 ECharts（年表除外，它是純 SVG／CSS grid，不需要圖表庫）。

**補上**（純增益，不違背舊語彙）：色階圖例、hover/focus tooltip、鍵盤可達性（舊碼的 `rect` 沒有 `role` / `tabindex` / `aria-label`，螢幕閱讀器完全取不到資料）。

### 5.6 可存取性

ECharts heatmap **不支援 decal**，所以色盲友善完全靠單色相明度階（§1.3 已驗算單調）。此外每張圖必須提供：

- `aria-label` 描述圖表在說什麼
- 一份**資料表 fallback**（`<details>` 收合的 `UTable`），螢幕閱讀器與「我就是想看數字」的使用者共用
- 格子可 focus，`Enter` 等同點擊

## 6. 動態

**只有一個編排過的時刻**：存檔成功後，新的紀錄列「印」進帳本——由上而下 180ms 的 reveal，只動 `transform` 與 `opacity`。像熱感應印表機吐出票根，而且它回應的是使用者剛完成的動作、顯示了什麼改變。

其餘一律沒有進場動畫。沒有逐區塊的 fade-and-slide-up，沒有每張卡片的 hover transition。

- 互動回饋 ≤ 200ms，`ease-out`
- 只動 compositor 屬性（`transform` / `opacity`）
- 尊重 `prefers-reduced-motion`：改為直接出現
- 不對大面積 `blur()` / `backdrop-filter` 做動畫

## 7. 明暗模式

由 `@nuxt/ui` 自動註冊的 `@nuxtjs/color-mode` 以 `.dark` / `.light` class 驅動（`classSuffix` 被強制設為空字串）。

**兩個模式都是「收藏冊」，差別是在哪裡翻它。**

| | 亮色：**散場後的商場走道** | 暗色：**放映廳** |
|---|---|---|
| 冊頁台紙（`body`） | `paper-50` `#F8EDDC` | `paper-950` `#1D1610` |
| 票根紙（`--ui-bg`：卡片／彈窗／輸入框） | `paper-25` `#FDF9F1` | `paper-900` `#29211A` |
| 主文字 | `paper-900` | `paper-50` |
| 內文 | `paper-700` | `paper-200` |
| 重點 | `amber-600` | `amber-400` |

**暗色不是把亮色反相，是換一組。** 兩個模式的**紙／票根層級關係一致**（台紙較深、票根較亮），
所以「票根貼在冊頁上」這件事在兩個模式都成立——這是這一版最需要在截圖上確認的東西。

暗色底是**暖褐**（`#1D1610`，HSL 色相 27.7），不是近黑。這是刻意的：
§0 的硬約束是「不要近黑底 + 螢光重點色」，那是 Letterboxd 的簽名（`#14181C` + `#00E054`）。
把暗底抬到相對亮度 0.0060 並帶進暖色相，讀起來是**光線調暗的房間**而不是 OLED 黑。

⚠️ **代價已量化**：暗底變亮壓縮了墨階的動態範圍，
出席圖「1 場 ↔ 2 場」的次要區分從 2.78:1 掉到 2.53:1（§1.3 有完整說明與補救）。

墨階在暗色模式**整條反轉**（紙色在高值端），不是把亮色階調暗——實測舊專案那三階深綠 `#18541c / #134016 / #0d2d0f` 在暗底上會直接消失。

琥珀在兩個模式維持同一 hue，只換明度端點：亮色用 `amber-600`，暗色用 `amber-400`。
⚠️ Nuxt UI 的 `--ui-primary` 亮色派生自 **500** 不是 600，必須覆寫，見 §1.6。

## 8. 文案

繁體中文。主動語態。句子大小寫（中文本來就沒有大小寫——這正好讓我們自然避開 ALL-CAPS 眉標的陷阱）。

| 情境 | 寫 | 不寫 |
|---|---|---|
| 送出紀錄 | 記下來 | 送出、提交 |
| 完成 toast | 記好了 | 成功！ |
| 搜尋無結果 | 找不到這部片？自己新增 | 查無資料、沒有結果 |
| 全新帳號 | 記下你的第一場 | 尚無紀錄 |
| 票價隱私 | 公開票價 | 啟用、開啟票價功能 |
| 刪除確認 | 刪掉這筆 | 確定要刪除嗎？ |

三條規矩：

1. 動作名稱從頭到尾一致——按鈕寫「記下來」，toast 就寫「記好了」，不會變成「已儲存」。
2. 錯誤說發生了什麼跟怎麼修，不道歉、不模糊。
3. 空狀態是邀請，給一個明確的下一步動作。

政府資料開放授權條款第 1 版：「未盡顯名標示義務者，**視為自始未取得授權**」。

- `This product uses the TMDB API but is not endorsed or certified by TMDB.` + TMDB logo

海報一律熱連結 `image.tmdb.org`，**絕不自建海報代理**——那等同轉存。

## 10. 品質底線

- 響應式到 375px；`h-dvh` 不用 `h-screen`；固定元素尊重 `safe-area-inset`
- 每個互動元件有可見的 focus ring（琥珀，2px offset）
- 只有圖示的按鈕一定有 `aria-label`
- 破壞性動作用 `UModal` 二次確認
- 載入態用結構性骨架（`USkeleton`），不用轉圈
- 錯誤顯示在動作發生的地方旁邊
- 寬內容（表格、圖表、程式碼）在自己的 `overflow-x: auto` 容器內捲動，**頁面 body 永遠不橫向捲動**
- 固定的 z-index 階，不用任意值
- 數字一律 `tabular-nums`（由 Inter 供應，見 §2.2）
