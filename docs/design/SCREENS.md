### 0.1 全站外殼／頂部導覽列（TopBar）

> **詞彙對照：David 口中的「TopBar」＝ `app/layouts/default.vue` 裡那個 `<header>`。**
> 這個 repo **沒有** `AppTopBar.vue`；全 repo grep「TopBar」只有一命中，就是那個 `<header>`
> 自己的註解。刻意不抽成元件（擴大 diff、與需求無關）。
> `app/layouts/` 底下只有 `default.vue` 一個檔，沒有頁面寫 `layout: false`，也沒有 `app/error.vue`
> ⇒ **22 條路由全部吃這一條**（2026-09-08 實查：`app/pages/**` 有 25 個 `.vue`，其中
> `admin/-AdminShell.vue`、`admin/-StaffGate.vue`、`admin/-TmdbMaintenance.vue` 是 `-` 開頭的
> 私有元件、不是路由）。

| 項目 | 值 | 為什麼 |
|---|---|---|
| 定位 | `sticky top-0`，**常駐** | 2026-09-07 David 逐字：「TopBar 要 sticky 在頂部」。**不做「往下捲收起」**——需求沒說，而且 auto-hide 會跟 `/app/records` 的橫向捲動手勢打架 |
| 列高 | `h-14` = 56px，**＋`border-b` 1px ⇒ 總高 57px** | 刻意不用 Nuxt UI 的 `--ui-header-height`（4rem = 64px）：那會平白長高 8px，而且覆寫它會連動 modal／slideover／sidebar 的計算 |
| 底色 | `bg-default`，**alpha = 1** | **不做毛玻璃。** 官方 `UHeader` 是 `bg-default/75 backdrop-blur-sm`，但 §0「不用漸層。不用發光。」，而且首頁 hero 是整面海報牆（`index.vue` 記過次要文字 4.11:1 的舊帳）——半透明壓上去會重演同一個事故 |
| z-index | `z-30` | 見 DS §10 的 z 階。必須 > 1：`/app/records` 釘住的 `<th>` 帶 `z-1`，而它的祖先都不建立堆疊脈絡，那個 1 一路穿到根脈絡 |
| 行動裝置佔比 | 375×667 佔 **8.55%**（剩 610px）；375×812 7.02%；390×844 6.75%；393×852 6.69% | 用 CSS 視窗高算的；`dvh` 會隨工具列收合而變小，所以 8.55% 是下限 |
| `<main>` | **不需要 padding-top** | sticky 仍佔正常流的位置，不會蓋住內容也不會跳版 |

**兩個「不要」：**

- ⚠️ **不要加 `scroll-padding-top`。** `LegalProse.vue:38,45` 與 `legal/copyright.vue:45` 的標題已經有
  `scroll-mt-20`（80px），對 57px 的導覽列還有 23px 餘裕。而 `scroll-padding` 與 `scroll-margin` 是
  **相加**的：加 56px 之後錨點會停在 136px，標題底下空一大塊。
  代價已知並接受：長表單（`/app/records/new`、`/app/records/[id]/edit`、`/app/settings`）Shift+Tab
  往回走時，焦點元素會被捲到視窗頂端、被 57px 的導覽列蓋住 focus ring。真要修，就得**在同一個 commit 裡**
  加 `scroll-padding-top` 並把那三處的 `scroll-mt-20` 一起降成 `scroll-mt-4`——**最糟的是只做一半**。
- ⚠️ **`UDrawer` 不要打開 `shouldScaleBackground`。** vaul 會對 `[data-vaul-drawer-wrapper]` 下
  `transform: scale(...)`，transform 祖先會變成 containing block ⇒ **抽屜開著時 sticky 導覽列會當場失效**
  （`position: fixed` 的東西也會一起錯位）。目前兩個呼叫點（`app/pages/app/index.vue`、
  `app/pages/u/[username].vue`）都沒傳這個 prop（預設 false）。

**跟著導覽列走的偏移（改列高要一起改）：** 目前有兩處抄了這個 57：

1. `app/components/LegalDocumentView.vue` 桌機側邊目錄的 `md:top-18`（= 72px = 56 + 邊框 1 + 呼吸 15）。
2. `app/components/YearScopeBar.vue` 的 `HEADER_H = 57`（2026-09-14 加）：它同時當
   IntersectionObserver 的 `rootMargin` 與「年表捲到導覽列上方了沒」的判準（§2.1）。

⚠️ 兩處都**沒有任何機制**會在列高改掉時變紅——症狀分別是「側邊目錄與導覽列之間多一條縫」
與「年份切換器早 57px／晚 57px 出現」，兩個都只有肉眼看得到。

**導覽列裡的 teleport 落點 `#header-year-scope`（2026-09-14 David 裁決）：** 夾在字標與
`AppNav` 之間、**永遠存在、預設是空的**。誰會 teleport 進來、什麼時候出現，見 §2.1。
⚠️ **它空著的時候不可以佔位**：身上不可以有 padding／margin／`flex-1`，這一行也不要改成
`gap-*`（那會在它空著的時候憑空多出兩道間隙）。空 div 寬 0 高 0 ⇒ 字標仍然靠左、`AppNav`
仍然靠右，視覺差異是零——這是它能一直掛在那裡的唯一理由。

**未決：** layout 根 div（`default.vue:2`）是 `bg-default` = paper-25／paper-900，而 `main.css` 給 body 的是
DS §1.1 的冊頁台紙 paper-50／paper-950。兩者對不上是既有問題（連帶讓 DS 行 230「圖表必須放在卡片上，
不要直接放在裸台紙上」目前是空轉的——整頁已經都是票根紙了）。**這一輪刻意沒改**，等 David 裁決；
改的時候 header 的底色必須同一輪一起改，否則會多出一條色帶（亮差 (5,12,21)、暗差 (12,11,10)）。

**後續選項備忘（2026-09-07 評估過，這一輪刻意沒走）：** z 階目前是**逐元件覆寫**
（`app/app.config.ts` 列了 9 個：modal／drawer／slideover／dropdownMenu／contextMenu／select／
selectMenu／popover／tooltip）。另一條路是把所有 portal 集中到自建落點——`app/app.vue` 改成
`<UApp :locale="zh_tw" portal="#fn-overlays">` 並在旁邊放一個 `<div id="fn-overlays" class="relative z-50" />`，
這樣只有一個落點、不需要維護元件清單（`App.vue` 的 `portal` prop 預設 `"body"`，`usePortal.js`
把它變成 Teleport 的 `to`）。它比逐元件覆寫更耐得住後續需求（要加 `UTooltip`、可能加 `UPopover`），
**但走之前必須先驗兩件事**：① toaster 的 `z-[100]` 會變成相對於那個新脈絡（行為不變，但這張階表的
語意要一起改寫）；② SSR 那一版的 `#fn-overlays` 要早於第一個覆蓋層存在。

### 2.0 圖表的資料從哪裡來（三條，違反會出事）

1. **圖表一律走 `/api/u/{username}/stats`（明確使用 anon client），
   不在前端拿紀錄列表就地算。** 列表是分頁的（一次最多 200 筆），就地算會讓
   超過 200 筆的使用者**年表缺格子而且沒有任何提示**。而那支端點與列表走
   同一條匿名路徑 ⇒ **圖與列表永遠是同一個母體**。
   （這一條原本就寫在 §9c.1 的精神裡，但實作曾經是從 `items` 就地算的。）

2. **⚠️ 那支端點逐欄挑「白名單」，金額欄位一個都不回。**
   `user_year_stats` 的回傳裡有 `totals.spend`、`monthly[].spend`、
   `monthly_baseline[].avg_spend`；匿名視角下它們一律是 **0**，
   而 **0 比不給更糟——它會被讀成「這個人沒花錢」**。
   > **為什麼是白名單不是黑名單**（這是最容易被日後「簡化」掉的一條）：
   > 黑名單是「把已知的金額欄位刪掉」，白名單是「只放行已知安全的欄位」。
   > 日後 `user_year_stats` 多一個帶金額的欄位時——它一定會，因為那支 RPC
   > 同時服務 `/app` 的儀表板——**黑名單會自動把它放出去，白名單不會**。
   > 差別在失敗方向：黑名單漏掉一個欄位＝洩漏；白名單漏掉一個欄位＝少一張圖。
   > 少一張圖看得見，洩漏看不見。

3. **金額只存在於 client 端**（`useUserSpend()`，`server: false`，帶觀看者
   自己的 session ⇒ RLS 依觀看者決定）。`/u/` 是 SSR，任何在伺服器端算出來的
   金額都會被序列化進 `__NUXT_DATA__` 一起送出。
   ⚠️ 頁首那句「花了 NT$…」與「每年花費」那條 band **共用同一次請求**：
   兩份查詢一定會在某次修改後對「看不看得到」「是不是全部」給出不同答案，
   而沒有人會發現——沒有人會把同一頁的兩個地方擺在一起看。

### 2.0b 「每年花費」對三種觀看者長得不一樣

| 觀看者 | 看到什麼 |
|---|---|
| 本人 | 全部票價。缺的幾筆是**自己沒記** |
| 路人 ＋ `show_cost = true` | 公開紀錄的票價。缺的幾筆是**沒公開** |
| 路人 ＋ `show_cost = false` | **一列都拿不到 ⇒ 整條 band 與頁首那句都不存在** |

> **第四種：`/app`，本人自己的儀表板。** 永遠看得到全部——但「全部」不等於「完整」。
> 實測 David 174 筆裡有 5 筆沒有票價列（2026-09-08 唯讀覆核：2024 年 3 筆、2020 年 2 筆，
> 全部是《少女與戰車 最終章》的連映拆分，票價記在第一筆），所以 **2020 與 2024 兩年在本人
> 自己的儀表板上就是「NT$6,260 以上」「NT$7,236 以上」**。`spend_is_partial` 不是只在路人視角
> 才會發生的事；那 5 筆的意思是「自己沒記」，不是「沒公開」，文案不可共用
> （`SpendByYear` 的 `isOwn` 就是在分這個）。
>
> `/app` 傳 `:privacy-note="false"`：「只有你看得到這些數字。」是為 `/u/` 寫的（那一頁的問題是
> 「我分享出去別人看到什麼」），`/app` 整頁私密，那句在那裡沒有回答任何問題。

**「時有時無」是要設計的東西，不是要迴避的東西**（David 2026-09-06 裁決，
推翻了「乾脆不做金額圖表」的提案）。落實成四條：

1. **判斷不由前端做，由 RLS 做。** 判準是「**讀得到幾列票價**」
   （`spend_known_records > 0`），不是「總額大於零」——後者會把
   「全部都是兌換票（NT$0）」誤判成「看不到」。
2. **不存在就是不存在**（§12-3）：不是畫成 0、不是打馬賽克、**不留佔位**（§12-4）。
   band 排在 band 堆疊的最後，而且刻意不給 `#fallback` 骨架——
   給固定高度骨架的話，拿不到金額的觀看者會看到一塊先撐開再塌掉的空白，
   那不但是版面跳動，還等於公告「這裡本來有東西」。
3. **`spend_is_partial` 要看得出來，而且是逐年的。** 兩層缺一不可：
   **① 數字本身**寫「NT$6,890 **以上**」——它跟著數字走，使用者只截到一列時
   那個但書仍然在；**② 長條右緣是虛線開口**，形狀也在說「還沒完」
   （不能只靠色差，墨階相鄰階低於 WCAG 1.4.11 的 3:1）。
   ⚠️ 用**逐年**的旗標。全期那個只要任何一年有未公開票價就是 true，
   標上去會讓每一年都掛著同一個但書＝等於沒標。
4. **NT$0 不等於隱藏**（同 §12.1）。實測 David **2015 年 2 場、票價都記了、
   合計 NT$0**（兌換票）。第一版把「金額為 0」當成「沒東西可看」整列過濾掉，
   結果**年表上有那一年、花費圖上沒有**，而畫面看起來完全正常。
   ⇒ 有紀錄就列，`0 且涵蓋完整` 顯示「**免費**」，條寬為 0
   （吃到「最小條寬」的話右邊寫免費、左邊畫一小段條，圖與字互相矛盾）。
   ⚠️ 但 `0 且涵蓋不完整` **仍然**是「NT$0 以上」——把它也寫成免費就是
   **把「沒公開」講成「沒花錢」**，是這張圖最不能犯的錯。
### 2.1 年表 YearStrip — 全站簽名

每年一列，一列 53 格（**每格是一週，不是一天**）。

**為什麼是週而不是日**：實測 169 筆分散在 12 年，日層級的填滿率約 6%——一張 7×53 的年格子有 96% 是空的，看起來不是「密度」而是「荒涼」。收成週之後填滿率跳到約 22%，2016–2020 的密集期與 2021–2022 的空窗立刻讀得出來。這是真實資料逼出來的偏離，不是懶。

- 純 SVG／CSS grid，**不需要圖表庫**（舊專案用 d3 手寫 imperative DOM，在 SSR 下是負擔）
- 格子 8×8px、間距 2px（節距 10）→ 一列 530px。手機上縮到 5×5px（節距 7）→ 371px，**剛好塞得進 375px，不需要橫向捲動**
- 色階：**三階**，0 場 → `heat-0`；1 場 → `heat-4`；2 場以上 → `heat-6`
  - ⚠️ **這一行 2026-09-06 修正過，舊值是壞的。** 原本寫 `heat-0/2/4/6` 四階，兩個問題：
    (a) 用了**相鄰階**，最關鍵的「沒去 ↔ 有去」只有 **1.84:1（亮）／1.94:1（暗）**，違反 `DESIGN_SYSTEM §1.3` 自己訂的規則，也低於 WCAG 1.4.11 的 3:1；
    (b) 第四階**永遠不會被畫出來**。實數（從本頁 mockup 的真實資料重算，689 個週格）：**537 週 0 場、135 週 1 場、17 週 2 場、`≥3 場` 0 週**。填滿率 22.1%，與本節「收成週跳到約 22%」對得上。
  - 改成 `heat-0/4/6` 之後，關鍵區分是 **5.05:1（亮）／4.60:1（暗）**，與年度出席圖同一組取值。
  - 上述分布是在**週日起始**下分桶算的。改成週一起始（`DESIGN_SYSTEM §5.4`）之後，週六與週日會落進同一桶，`2 場`的週數只會**變多**、不會出現 `≥3`，所以三階仍然成立；真實資料接上後重算一次即可。
- 右側對齊該年總場次，Inter `tabular-nums`
- **它同時是年份選擇器。** 點某一列 → 該年成為 active（**琥珀左邊框 ＋ 粗體年份 ＋ `bg-accented` 底色**——2026-09-14 照實作更正：實作從來沒有 `▸` 標記，底色是這一輪為了「看得出可以點」加的，見下一條），下方列表與統計跟著換。這解決了「年份下拉選單會讓人選到只有 2 筆的 2015 年」的問題——你在選之前就看得到那年有多少東西。
- 鍵盤：`↑↓` 換年、`Enter` 選定；每列有 `aria-label="2019 年 25 場"`
- **「年份可以點」這件事本身要看得見**（David 2026-09-14 第 2 點前半：「年表的年份能點擊
  這件事不太明顯」）。落點 `YearStrip.vue`：hover／focus-visible／選中**共用同一個底色**
  `bg-accented`——hover 的意思就是「按下去會變成這樣」，不發明第三種色階；選中另外靠左邊
  那條琥珀邊框與粗體年份區分。
  - ⚠️ **底色不可以用 `bg-elevated`。** 亮色的它逐字等於空白週那一格的顏色（`att[0]`，
    同為 `#EADDCA`）⇒ hover 上去那一列的 53 格會整條消失（1.00:1），看起來像畫面壞掉；
    暗色也只有 1.06:1。`bg-accented` 對 `att[0]` 是 1.18:1／1.29:1，兩個模式都還讀得出來。
    **要改這裡的底色，先去 `app/utils/chart-theme.ts` 對一次 `att[0]` 的值**（數字寫在
    `YearStrip.vue` 的模板註解裡）。
  - ⚠️ **不加 transition、不改列高、不改左邊框寬度**：`DS §6` 逐字寫著「沒有每張卡片的
    hover transition」，而且 13 列同時在畫面上，逐列淡入淡出會讓整張年表看起來在呼吸；
    列高或邊框一動，整條年表會在 hover 時逐列跳版。
  - 清單底下多一句提示（「點一列就只看那一年；最上面那列回到全部年度」）。
    ⚠️ **那句話不可以放進 listbox 裡面**——listbox 的子節點只能是選項，塞一段散文進去，
    螢幕閱讀器要嘛把它唸成一個選項、要嘛整個跳過。它是 listbox 的**兄弟**，用
    `aria-describedby` 接回去；`interactive: false`（只當門面的呼叫端）不出現這一句。
    後半句只有在真的有「全部年度」那一列時才講。

**往下滑之後，年份切換器出現在導覽列上**（David 2026-09-14 第 2 點後半：「往下滑時希望
header 也有選項可以直接切換年份」）。落點是 `app/components/YearScopeBar.vue` ＋
`app/layouts/default.vue` 的 `#header-year-scope`。它解決的是「捲下去之後就切不了年份」——
年表坐在第一條 band，捲到熱點圖、去了哪裡、票根列表之後，全站唯一的年份選擇器已經在畫面外。

- **它是 Teleport 進既有的那一條導覽列，不是第二條 sticky bar。** 第二條 bar 得釘 `top-[57px]`，
  而 57 是**抄** `default.vue` 的 `h-14` ＋ `border-b` 抄來的手調常數（§0.1）：列高一改，它不會
  編譯失敗、不會有測試變紅，只會在某個畫面上靜靜錯開一條縫。而且多一層 sticky 就多一組
  z-index 要跟 `UDrawer` 的遮罩（50，見 `app/app.config.ts` 的 z 階）對帳。Teleport 進去，
  位置由導覽列自己決定、z 階直接繼承它的 30，兩件事都不會發生。
- **落點永遠存在、預設是空的**，夾在字標與 `AppNav` 之間（規格與限制見 §0.1）。
- **顯示判準是「年表已經捲到導覽列上方」，不是「年表不在視窗裡」。** 元件在原地
  （呼叫端把它放在年表那條 band 後面）留一個 1px 的 sentinel，判準是
  **「不相交」且 `boundingClientRect.bottom < 57`**。
  - ⚠️ **只看 `isIntersecting` 是錯的**：sentinel 還在**視窗下方**（使用者根本還沒捲到）時
    它同樣是 false ⇒ `/app` 一載入、年表明明就在畫面上，導覽列上已經多出一個一模一樣的
    選擇器，同一個選擇同時有兩個入口。所以要再問一句「它是從**上面**離開的嗎」。
  - ⚠️ 還要把 observer 的 root 上緣往下推 57px（`rootMargin`）。預設 root 是視窗，
    `isIntersecting` 要到 sentinel 完全越過 y=0 才翻面，那時 `bottom < 57` 早就成立
    ⇒ 上面那一句會退化成永遠為真的裝飾，而切換器**晚 57px 才出現**（sentinel 被導覽列蓋住的
    那一段路，它還沒現身）。兩處用同一個常數（`HEADER_H`）。
  - observer 在元件卸載時要自己 disconnect——換頁時它不會自己停，而它抓著一個已經不在
    文件裡的節點。
- **這一段包 `<ClientOnly>`。** `/u/[username]` 是 SSR 頁，而 Teleport 的目標在伺服器端是用
  字串比對去找的，指到一個還沒 render 出來的容器時行為不穩（警告，或內容落在錯的地方）。
  這條 bar 初值本來就是隱藏的 ⇒ SSR 少畫它**不會少畫任何東西**，包起來零代價。
- **只動 opacity，150ms，`motion-reduce:transition-none`。** ⚠️ **不可以用位移或高度動畫**：
  導覽列的高度一變，它底下的整頁內容就會跟著跳（`h-14` 是版面的地基，§0.1）。這不算
  `DS §6` 禁的「進場動畫」——它回應的是使用者自己的捲動，屬於互動回饋（≤200ms、只動
  compositor 屬性，兩條硬規則都守著）。這個 repo **沒有**全域的 reduced-motion 規則，
  每一處自己加。
- **選單是 checkbox 型的下拉，不是 `USelect`。** `USelect` 的 `v-model` 收不到 `null`——那是
  它的「還沒選」狀態、會顯示 placeholder，而這裡的 `null` 是一個**正當的值**（全部年度，
  與 `YearStrip` 同一個語意）。要用它就得自己發明一個哨符字串再翻譯回來，那條路上有兩個
  可以寫錯的地方。⚠️ checkbox 的回呼帶的是**新的**勾選狀態：點已經勾起來的那一項會收到
  `false`，而這一組是單選（不存在「什麼都沒選」）⇒ 只在為真時才送出。
- **375px 下那顆鈕必須壓在 60px 上下。** 那一行還要塞字標（約 45px）＋「filmnote」（約 46px）
  ＋右上功能選單（約 120–150px），扣掉左右內距之後可用寬 343px。所以它比 `AppNav` 小一階、
  不畫框，而且「全部年度」在 `sm` 以下只印「全部」（選單裡與 `aria-label` 仍然唸完整的四個字）。
  ⚠️ **不要為了更窄再降一級**：量到的鈕高 24px，正好踩在 WCAG 2.5.8 的 24×24 下限上。
- **一筆紀錄都沒有的公開頁不出現這顆鈕**（`years.length` 的守門）——一個只剩「全部年度」
  的選擇器選不出任何東西。
- 年份的排序由這支元件**自己再排一次**（新到舊），不假設呼叫端的順序：`/app` 與 `/u/` 的
  `stripRows` 是各自算的，哪天上游被改動，選單的順序不會無聲地反過來。

## 3. `/u/[username]/[year]` 年度回顧（SSR，不快取）

⚠️ **這是全站首屏成本最高的一頁**：`routeRules` 給 `/u/**` 的是 `cache-control: private, no-store`（RLS 依觀看者而異，絕不可快取），而圖表 100% 在 client 端算。骨架必須做好。

Letterboxd 的 Year in Review 是編輯式長捲頁而不是 dashboard（14 個具名章節、每節整版換底色、委製插畫）。**年度回顧與日常 App 是兩個不同的設計語域，這是可以放大的許可證。**

章節（每節整版，垂直捲動）：

1. **這一年** — 年份數字設到 72px，年表該列放大
2. **去了幾次** — 年度出席圖（7×53 日格）
3. **什麼時候看** — 時段熱點圖 + 一句話結論（「你 71% 的場次在週五到週日的晚上」）
4. **在哪裡看** — 影城分布橫條 + 主場那一句

> ### 🔸 2026-09-06 David 裁決：**檢視視角預設「全部年度」，可切換指定年份**
>
> 原文：「預設用全部（個人所有資料）的檢視視角，可切換指定年份顯示，
> 全部顯示視角下無法呈現的（像是逐日貢獻圖）就隱藏」。**`/app` 與 `/u/` 一致**
> ——同一個名字的圖在兩頁有兩種語意會讓使用者以為資料錯了（`backend.md §6e`）。
>
> **這比翻一個預設值大。** 改之前 UI 上**根本到不了**全期視角，而程式看起來支援：
>
> - `YearStrip` 的 emit 型別是 `[year: number]` ⇒ 永遠 emit 不出 `null`
> - `activeYear` 起始就是 `available_years[0]`（最新年度），之後只能換成另一個年份
> - 所以模板裡那些 `activeYear === null ? …` 全部是**跑不到的死分支**
>
> **實作上的四條規矩**：
>
> 1. **回到全期必須是看得見的一個選項。** `YearStrip` 最上面多一列「全部年度」，
>    有 `aria-selected`、鍵盤走得到、預設就是它。**不要做成「再點一次同一年回到全部」**
>    ——年表是這一頁的檢視選擇器，選擇器不能有一個選不到、只能猜出來的狀態，
>    尤其它還是預設值。
> 2. **全期下畫不出來的 band 整條不出現**，不是畫成空的、不是畫成「0 年」。
>    目前只有 **band 2 年度出席圖**（7×53 綁死在一個日曆年上）。
> 3. **每一句圖說都要說得出自己涵蓋什麼範圍。** 同一句話在兩種視角下長得一樣
>    而數字差十倍是最容易被讀成「資料錯了」的形狀。band 7 多刷排行尤其要注意：
>    它的語意會從「那一年內看過兩次」變成「這些年來看過兩次」。
>
>    **2026-09-07 補（這一條的第一個真實實例）：**「每年花費」是全站第一條
>    **範圍與旁邊的 band 不同**的 band——它恆為全期，而其他 band 跟著年份切換器走。
>    `/u/` 從上線起就是這個行為而畫面上沒有任何記號（本人視角只有一句
>    「只有你看得到這一段。」，路人視角是 `null`）。現在兩頁在**選了年份時**都會多一句
>    「這一條不隨上方的年份切換。」；全期視角不加那句，因為那時它與其他 band 同範圍。
> 4. **band 4 月度趨勢在全期時不畫平均線。** 全期的實線是「十三年同月加總」
>    （十月 24），虛線是同一組數字除以曝光數（2.00）——同一條 y 軸上虛線會貼著底
>    趴平，而且它在全期不再具有對照功能：它就是實線本身除以一個常數。
>    指定年份時它才回來，那才是它的用途（「整年 N 場，比歷年平均多／少」）。
>
> 頁面的標題數字（「總共看了 174 場、250 張票」）原本是 band 2 的 caption，
> 已提到**頁面層級**——否則全期視角下它會跟著 band 2 一起消失，
> 而那是全頁唯一說得出總數的地方。

### 9.1 時段軸的兩個真實決定，與格盤外的兩條總和

實測 David 的場次只落在 **9–23 時，外加 1 筆 0 時**。

1. **軸從 09:00 開始，不是 00:00。** 舊專案畫滿 24 列，前 9 列永遠全空，白白吃掉 1/3 的高度。
2. **00:00–02:00 折到最後，標為「午夜場」。** 週五深夜的午夜場在心理上屬於「週五晚上」，不是「週六凌晨」。把它放在行首會把一次連續的外出經驗切成兩天。

⚠️ `cartesian2d` heatmap 完全不畫空格，7×N 全格必須明確餵 `value: 0`，否則「從未」的格子會消失、露出卡片底色，看起來像破洞。

**3. 格盤外側有兩條總和軌道：底部一列是每個星期的總和，右側一欄是每個時段的總和。**

實作上它們是 ECharts 的**第二組 category 軸**（`xAxis[1]` / `yAxis[1]`）的純文字標籤，不是 heatmap
的格子。這不是實作偏好，是被數字逼出來的——實測 David（174 筆）**單格最大 9，而欄總和最大 60**，
差 6.7 倍（2026-09-08 唯讀 SQL 覆核：欄總和 6/5/13/13/41/60/36，單格最大 9）：

- 總和塞進 `grid.data` ⇒ `max` 從 9 變 60 ⇒ `heatPieces(60)` 第一段是 `{gt:0, lte:10}` ⇒ 真實的
  112 格（值域 0–9）**全部塌進最淺的兩階**，整張圖變平。
- 總和沿用 `max=9` 的色階 ⇒ `{gt:7}` 那一段把多數欄總和塗成最深的 `heat[6]`，**跟真正的尖峰同色**，
  色階的語意當場失效。

**兩種都零錯誤訊息。** 所以 `HourGrid` 的 `colTotals` / `rowTotals` / `total` 是**與 `data`、`max`
嚴格隔離**的三個欄位（`app/utils/stats.ts`）。

⚠️ **總計（174）不放在圖上**——頁面標題那行已經有了，而且在有 `records_without_time` 的帳號上
兩個數字本來就會不一樣（熱點圖的母體是 `watched_time is not null` 的那一份）。

⚠️ 兩條總和軸都寫 `interval: 0`（`app/utils/hour-heatmap-option.ts:95`）。category 軸的
`axisLabel.interval` 預設是 `'auto'`，標籤要撞在一起時會**靜靜丟掉幾個**，而掉一個總和的症狀是
「那一格看起來是 0 場」，零錯誤訊息。

### 9.2 點格子 → 底部片單

舊專案最有價值的互動語彙，原樣保留，並在 **2026-09-14 David 裁決**之後擴到整頁
（原話：「每個月、去哪裡、看的是什麼 也能點擊展開列表」）：
點出席圖的一格、熱點圖的一格、**熱點圖外側的任一個總和**、
**band 4 月度趨勢的一個月份**（x 軸的月份標籤**或**實線上的資料點，兩條路徑開同一個抽屜）、
**band 5／6 分布長條的任一「一般列」**（含「其他 N 家」展開出來的每一列；聚合列本身的手勢是
展開、不是開抽屜，見 §9.5 規矩 4）、或 **band 7 多刷排行的一列**
→ `UDrawer direction="bottom"`，高度 90%，內容是該範圍的票根卡清單（`show-year` 必給）。

標題格式（分隔一律「量詞＋全形空白 U+3000」，**不用中點**）：

| 點什麼 | 標題 | 由誰組 |
| --- | --- | --- |
| 出席圖的一天 | `2024/03/15（週五）` | `dayTitle()` |
| 熱點圖的一格 | `週五　21:00` | `slotTitle()` |
| 底部的星期總和 | `週六　全部時段` | `weekdayTitle()` |
| 右側的時段總和 | `21:00　全部星期` | `hourRowTitle()` |
| band 7 的一列 | `少女與戰車 劇場版　10 次`（全期）／`少女與戰車 最終章 第４話　2024 年　3 次`（指定年份） | `repeatTitle()` |
| band 4「每個月」的一個月份 | `3 月　12 場`（全期）／`2019 年 3 月　4 場`（指定年份） | `monthTitle()` |
| band 5「去了哪裡」的一列 | `林口威秀影城　120 場` | `distPickTitle()` |
| band 6「看的是什麼」版本的一列 | `4DX　30 場`（名稱來自 `screening_format.label`，不是 code；「其他　5 場」也是一個**真分類**，見下） | `distPickTitle()` |
| band 6「看的是什麼」國別的一列 | `日本　102 場`（沒有國別的那一列是 `未分類　N 場`） | `distPickTitle()` |

⚠️ **星期總和那一條的過濾必須排除沒記時間的紀錄。** 熱點圖的母體是 RPC 的 `weekday_hour`
（那支 SQL 帶 `where watched_time is not null`），而頁面手上的 `records` 是全部。少了這個條件，
抽屜列出的張數會比圖上的總和多——而唯一有資料的帳號 `records_without_time = 0`，
**點一百次也不會現形**。所以述詞寫在 `app/utils/stats.ts` 的 `matchesWeekdayPick()` 裡由單元測試
釘住，不寫在 `.vue` 的 inline computed（那樣 vitest 摸不到）。

⚠️ **`monthTitle()` 的分隔有兩層，不要「順手統一」。** 規矩其實是同一條：**複合詞內部
（數字＋量詞、年＋月）用半形空白，只有最後那一組量詞前面才是 U+3000**。所以
`2019 年` 與 `3 月` 之間是半形，`3 月` 與 `12 場` 之間才是全形——與 `repeatTitle()` 的
`…　2024 年　3 次` 是同一條規矩的兩個實例。把中間那個半形「統一成全形」，標題看起來會多一個字。

⚠️ **「每個月」在全期視角下是季節性，不是某一年的某個月。** band 4 全期的一點是**十三年同月的
加總**（三月＝ 2014 的三月 ＋ … ＋ 2026 的三月），所以 `MonthlyTrend` 只 emit 月份（1..12），
年份由呼叫端補。述詞是 `app/utils/stats.ts` 的 `inMonth()`，它**只管月份不管年份**——
指定年份時呼叫端**必須另外**加年份條件，否則切到 2019 年會把十三年的三月全列進抽屜
——圖上那一點說 N，抽屜列出好幾倍，而兩邊都「看起來正常」。
⚠️ `inMonth()` 一律**字串切片**解析 `YYYY-MM-DD` 的第 6–7 碼，**不可以 `new Date()`**：
`watched_on` 是台北牆上時間的日期，`new Date('2026-03-01')` 會被當成 UTC 午夜再轉本地時間，
UTC 以西整個**退一天** ⇒ 月初那一筆掉到上個月，圖上 12 筆、抽屜列 11 張，兩邊都「看起來正常」。
（同一條理由已經寫在同檔的 `weekIndexInYear()`／`isoDow()`／`inRepeatScope()` 上。）

- `format`：RPC 是 `coalesce(r.format_code, 'other')` ⇒ 述詞也要 `?? 'other'`。
  ★ 這不是假想邊界：實測 David 的版本分布是 digital 129 / 4dx 30 / imax 9 / **other 5** /
  dolby 1，畫面上那個「其他」是一個**真分類**（不是 `topWithRest()` 聚出來的長尾），
  少了這個 coalesce，`format_code` 為 null 的紀錄會在圖上算進「其他」、在抽屜裡一筆都不見。
- `country`：RPC 是 `coalesce(f.country, '')`，**空字串就是畫面上的「未分類」**
  （讀不到 film 的私密 UGC 作品也落在這一桶）。拿「未分類」這四個字去比對什麼都對不上。
- `venue`：RPC 直接 group by `r.venue_id`，沒有場所的是 null ⇒ 述詞用 `?? ''`，呼叫端那一列的
  key 也寫成 `venue_id ?? ''`。
⇒ 所以 `DistItem` 帶的是**穩定識別 `key`**（venue_id／format code／country 字串），**不是名稱**：
同名分館會撞，而聚合列的 `key` 是 `null`（它不是一個分類，是好幾個分類的和，點它的手勢也不是
開抽屜）。⚠️ `topWithRest()` 必須**原樣帶過**每一件的 `key`（head 與 rest 裡的都要）——
在那裡重建物件就會漏掉它，而漏掉的症狀是「長條畫得出來、點下去抽屜永遠是空的」，
typecheck 與既有測試都不會紅（`key` 是可選欄位）。
⇒ 這三條 coalesce 與 `inMonth()` 一樣，都寫成 `app/utils/stats.ts` 的匯出純函式由 vitest 釘住，
不寫在 `.vue` 的 inline computed——**vitest 摸不到 SFC**，而它們壞掉的樣子全都是
「抽屜開得起來但少列了幾張」，沒有錯誤訊息。

band 4 是折線那一點的高度、band 5／6 是長條右邊那個數字——`repeatTitle()`／`monthTitle()`／
`distPickTitle()` 三支都把它當**必填參數**，就是為了不讓人偷懶改用抽屜自己的長度（用同一個
來源組標題就永遠對得起來，也就永遠看不出錯）。不一致時要被肉眼看見（踩雷 #169：抽屜開得起來

### 9.5 「其他 N 家」的展開

> **節號說明：** 這一節的內容在邏輯上屬於 9.2（互動），原始的改動請求也寫「放在 9.3 之後」。
> 但 **9.4 已經被「載入態」佔住，而 `docs/design/mockups/dashboard.html:477,1938` 兩處以
> 「§9.4」指名那一節**——重編號會讓那兩個指標指到別的東西，所以這一節排在 9.4 後面、編為 9.5。

分布長條的 head 是 5 條，長尾聚成「其他 N 家」（`app/utils/stats.ts` 的 `topWithRest()`）。
那一列**點得開**，展開後列出完整清單；**2026-09-14 David 裁決之後，其餘每一列也都點得開**
（一般列開的是底部抽屜、不是展開，見規矩 4）——所以這一節現在講的是整條分布長條的互動，
不只是「其他 N 家」那一列（節名與節號都照舊，理由見上面那段節號說明）。五條規矩：

1. **展開後維持同一把尺。** 長度基準永遠是最長那一條（head 第一列），不可以換成長尾自己的
   最大值。實測 David 全期，長尾裡 3 場的那一條若拿自己當滿版會被畫得跟 120 場的主場一樣長
   ——那比不展開更糟，因為它**看起來像資料**。代價是十根幾乎一樣短的小刺，那是誠實的代價。
2. **只多一筆時直接併進 head，不生「其他 1 家」。** 一顆點開只有一列的鈕是純粹的浪費。
   這不是假想邊界：實測全期的國別與版本**正好都是 5**（＝ limit），多一個沒看過的國別就會踩到。
   落點是 `topWithRest()` 的 `items.length <= limit + 1` 那一條。
3. **換年份自動收合。** 實測 13 個年度裡只有 2016（7 家）與全期（15 家）會長出「其他」那一列。
   ⚠️ 全期與 2016 **都是 6 列**，所以收合的觸發不可以看列數，要看 `items` 這個陣列參考本身
   （`DistributionBars.vue` 的 `watch(() => props.items, …)`）。
4. **每一列都可以點，但有兩種手勢——靠 chevron（那個小箭頭）分辨。**
   （2026-09-14 David 裁決改寫。舊版這一條寫的是「觸發區只包住名稱那一行，**其他長條
   一條都不能點**，讓長條吃點擊會誤導」——**那個前提已經被推翻**：David 第 4、5 點要求
   每一列都能列出底下的紀錄。）
   - **聚合列**（「其他 N 家／N 種／N 國」，**有**箭頭）：點它是**展開／收合**長尾。
     它的數字是加總，不對應任何一份列得出來的紀錄清單——不存在「那 17 場是哪些」。
   - **一般列**（其餘每一列，含展開出來的長尾，**都沒有**箭頭）：點它**開底部抽屜**，
     列出那一列對應的每一筆紀錄（標題與過濾見 §9.2）。
   ⇒ 箭頭是畫面上**唯一**分得出兩種手勢的線索：**不可以拿掉**（「其他 10 家」會看起來
     只是一行沒人要點的字），也**不可以「順手」給一般列也配一個**（兩種列長得一模一樣、
     點下去做不同的事，那比不能點更糟）。
   ⚠️ **「觸發區只包住『名稱＋數字』那一行、長條一條都不吃點擊」這半條仍然成立，但理由換了。**
     不再是「長條不能點」（現在整列都能點），而是**長條是資料，不是控制項**：兩種手勢底下的
     長條長得一模一樣，而聚合列那一條是**加總**。長條一旦吃點擊，同一個視覺元素在聚合列上
     是「展開」、在它正下方每一條上是「開抽屜」。
     **「長條從不接受點擊，接受點擊的是上面那一行字」是這裡唯一學得起來的規則。**
   ⚠️ 兩種手勢都是**按鈕 ＋ 狀態屬性**（聚合列是展開狀態、一般列宣告自己會開一個對話框），
     不是原生揭露元素、不是 `div @click`——與 §10.4 同一個裁決的形狀。理由完整寫在
     `DistributionBars.vue` 檔頭（那段註解刻意不寫屬性名的字面 token，踩雷 #166）。
   ★ hover 的回饋要在**三種列上各自成立**：head 第一列本來就是 `text-highlighted`，
     再給它一次同樣的顏色等於沒有回饋 ⇒ 一般列的 hover 改由**底線**承擔（不加 transition，
     `DS §6`「沒有每張卡片的 hover transition」），聚合列由顏色承擔。
   ★ 清單底下補一句提示（「點一列看是哪些紀錄」）：沒有它，「每一列都能點」只剩滑鼠指標的
     形狀在講，**觸控裝置上等於完全沒講**。那句話只有在**真的有聚合列時**才多講半句
     「有箭頭的那一列先展開」——13 個年度裡有 11 年根本沒有那一列，那幾年講它是在指一個
     畫面上不存在的東西。一列都沒有時整句不出現（不要讓提示指著一片空白）。
5. **展開後不縮排**（David 2026-09-14 第 3 點原話：「去了哪裡的其他 N 家我希望展開時不要縮排」）。
   落點是 `DistributionBars.vue` 展開清單那一層：原本帶著**一條左側框線 ＋ 12px 的左內縮**，
   兩個都拿掉，長尾的每一列與 head 切齊。
   ⚠️ **這不是喜好，內縮是真的錯的。** 全部長條共用同一把尺（規矩 1），內縮讓長尾的軌道
     少 12px ⇒ **同一個場次數在主列與在長尾裡量起來不一樣長**，尺自己說了謊。而手機上
     那十幾 px 佔容器寬的比例，比長尾那幾條彼此之間的差距（1 場 vs 2 場，且 1 場那幾條
     還吃 2% 的最小條寬）還大——被縮掉的量比它們要表達的資訊還多。
   ★ 縮排一拿掉，「這幾列是從上面那一列展開來的」就只剩箭頭的方向在承擔，而箭頭只有 14px、
     而且捲動之後聚合列會滑出畫面 ⇒ 補一條**上緣髮絲線**（`border-t border-default` ＋ `pt-3`，
     與既有的 `mt-3` 一起）把「上面是聚合列、下面是它的內容」切開。選它的理由：
     ① 不佔水平空間 ⇒ 長條切齊，尺不會說謊；② 是靜態邊框不是動畫 ⇒ 不違反 `DS §6`；
     ③ 與 `/app` 表格列 `border-t border-default` 同一個語彙，沒有新發明。
   考慮過但**否決**的三條：① 保留縮排（David 直接否決）；② 只靠箭頭（捲動後零線索）；
   ③ 展開動畫或背景色塊（`DS §6`「其餘一律沒有進場動畫」，而且背景色塊會跟長條的軌道色打架）。

**band note 補一句「共 N 個場所」**：收合時圖上只有 6 條，而頁首寫「去過 15 個場所」，
不講清楚會被讀成對不上。
⚠️ **這一句是規格，2026-09-08 實查尚未實作**——`/app` 的 band 5 只傳 `:insight`（而 David 的
資料會走到「你的主場是 …，69% 的場次在這裡。」那一支，句子裡沒有場所數），`DistributionBars`
也沒有總計列。要補的是 `ChartBand` 的 `:note`，不是把場所數塞進圖說（圖說有自己的門檻規矩，
見 §9c.3）。

### 9b.1 band 是卡片，不是裸長卷

§9 原本寫「垂直長卷、一個 band 一張圖」，mockup 也是開放的 band 用髮絲線分隔。
實作把每一條 band 包成一張 `bg-default` 的卡。**照實作。**

理由是我自己在 `DS §1.3` 訂的：圖表的零格對紙面要 1.27:1，放在裸台紙上只有 1.16:1。
圖表既然要坐在票根紙上，把整條 band（標題＋圖說＋圖）一起放上去比只讓圖表自己有底更整齊。

⚠️ 這**不是** `DS §4.4` 要避開的 stat tile 版面。差別在於：
一張卡 = 一條 band = **一張滿寬的圖 + 一句圖說**，不是一格一個大數字的磚牆。
**守住這個差別**：一旦有人把一張卡切成兩三個小方塊放數字，就變成儀表板了。

### 9b.2 一條 band 可以放兩張同類型的小圖

「看的是什麼」band 同時放了版本與國別兩個分布。**照實作。**
兩者都是三、四列的小分布，各自獨立一條 band 會讓頁面變得很長而且很空。
限制：**只有同類型、同視覺語彙的圖可以並排**，而且合起來仍然是一句圖說。

### 9b.3 區塊標題 18px

`DS §2.4` 寫 20px，實作是 18px。**照實作。**
20px 是給裸長卷上的區塊標題訂的；包進卡片之後卡片本身已經提供了分隔，
標題不需要那麼重。`DS §2.4` 的 20px 仍然適用於沒有卡片包覆的區塊標題。

### 9b.4 年表與分布長條不用圖表庫

實作改用 SVG／CSS grid。**照實作，而且這是對的**——
年表每一列要鍵盤可達（`canvas` 拿不到 focus），分布長條照 `DS §5.2` + `§1.3`
合起來的結論本來就是「名稱自己一行、條在下面」，那是 HTML 排版不是圖表。
順便拿到 375px 自動換行與螢幕閱讀器可讀。

`DS §5.1` 已經把年表列為「自製 SVG／CSS grid，不需要圖表庫」，
這裡把**分布長條**也一起納入同一條。

## 9c. 2026-09-06 對帳：實作要改的地方

### 9c.1 ⚠️ `/u/[username]` 沒有年表

§2.1 把 YearStrip 定為**全站簽名**，而且**兼任年份選擇器**。

### 9c.2 ⚠️ 時段熱點圖被縮到單一年份

> ### 🔸 2026-09-06 更新：這一條**已經結案，而且結案的方式跟本文原本寫的相反**。

### 9c.3 圖說不可以從雜訊裡推論

「你最常在週六 10:00 進場，共 2 場」——2 場，樣本 8 筆。
這是一個**從雜訊長出來的斷言**，比不給洞察更糟，因為它看起來像一個發現。

frontend 把圖說改成條件式（週末佔比過半才講週末，否則講尖峰時段）**是對的**，
本文認可。**樣本數門檻**：該 band 的資料點少於 **20** 筆時，圖說改成純敘述
（「2026 年的 8 場分佈在 5 個時段」），不要出現「最常」「主場」「你的」。
這同時解掉 §9.3 的空狀態問題：**0 筆不畫圖**、**1–19 筆畫圖但不給斷言**、
**20 筆以上才有洞察**。

> ### 🔸 2026-09-06 David 裁決：**總筆數門檻不夠，「最」要是真的**

**這一頁不是回顧頁，是維護後台。** 2026-09-06 David：「這邊比較像是個人的資料維護後台」。
整頁的每一個決定都從這句話長出來，包括那些**跟 `/u/`、`/app` 刻意不一致**的地方。

頁名就是這件事的第一個落點：**「個人紀錄管理」不叫「全部紀錄」**——後者講的是範圍

### 10.1 為什麼是表格，不是票根卡列表

**本節推翻了本文件的前一版。** 前一版寫「`UTable virtualize` 或票根卡列表二選一——
票根卡列表，因為它跟 `/u/` 的呈現一致，使用者不必學兩種版面」。
2026-09-06 David 指定改成 Table + 篩選，理由是**兩種呈現本來就在回答兩個不同的問題**：

- **票根卡是一筆一筆看**——公開頁、單筆分享、刪除確認框。要確認「刪的是哪一筆」時，
  一張看得出是什麼的卡片比一列對齊的欄位好。
- **表格是橫著比**——「我在哪家戲院花最多」「哪幾筆沒填票價」「哪幾筆是公開的」
  要對齊欄位才看得出來。

⚠️ **這不是 `TicketCard` 退場**：`/u/`、`/film/` 的「誰看過」、匯入預覽、
以及這一頁自己的刪除確認框都還在用它。

⚠️ **不用 `UTable` 的 `virtualize`**（要求容器有確定高度，踩雷 #54）。走分批載入
（一批 24 筆），單一年份大多在 30 筆以內。

### 10.3 日期為什麼跟票根卡不一樣（這一條會被下一棒想「修」回去）

`/u/`、`/app`、`/film/` 的日期帶是 `Jul` / `26 Sun` / `16:00`（`DESIGN_SYSTEM §4.3`）。
**這一頁不是**，它是 `2026/07/26 16:00`。

分界線是**頁面的性質，不是資料**：

- 回顧用的頁面在講一段經驗 ⇒ 票根語彙。
- **維護後台在對帳** ⇒ 機器可讀、可排序、可跟訂票紀錄／發票並排比對的標準格式。

⚠️ 這裡曾經有一行註解寫著「跟票根卡一致——使用者不會覺得同一份資料在兩頁該長得
不一樣」，David 2026-09-06 明確推翻了它。**看到兩頁格式不同不是 bug**，
要改回去之前先確認這一頁已經不再是維護後台。

⚠️ **沒有場次時間的列只印日期**（`2026/09/06`），不補 `--:--`。缺席靠「別的列後面
都有一截、這一列沒有」自己顯現；佔位符會變成一整欄的雜訊，而且讀起來像
「有一個時間但不給你看」（同 §12 第 4 條）。落點：`app/utils/format-datetime.ts`
的 `watchedAtText()`，有測試釘住。

### 10.4 備註與公開狀態

**備註**（自由文字，實測 174 筆裡 73 筆有、平均 14.3 字、最長 67 字、5 筆含換行）：

> **2026-09-07 David 裁決把這一段的機制換掉了：從「原地展開」改成「Tooltip ＋ Dialog」。**
> 舊機制（`aria-expanded` 的就地展開）**不是錯的，是被換掉的**——它在桌機上讀起來很順，
> 但它把「讀到全文」這條唯一路徑綁在一個原地長大的格子上，而那個格子在 375px 上要跟
> 固定操作欄搶同一片寬度。下面六條是新的規格；`aria-expanded` 在這一頁已經沒有了。

- 收起態把**所有空白含換行摺成一個空格**再判斷長短——判斷邏輯不能假設它是單行。
- **短備註（≤16 全形字且不含換行，實測 54/73）直接印在格子裡，而且折行不截字**。
  它沒有按鈕，截了全文就永遠讀不到。
- **長備註（>16 字或含換行，實測 19/73）是一顆 `<button>`（`aria-haspopup="dialog"`），
  點開 `UModal` 看全文**，**不是 `div @click`、不是 `title` 屬性、也不能只給 `UTooltip`**：
  `title` 與 `UTooltip` 在觸控裝置上是同一個失效模式（reka-ui 的 `TooltipTrigger` 對
  `pointerType === 'touch'` 的 pointermove 直接 return、隨後的 focus 被 `isPointerDown` 擋掉、
  click 直接 onClose ⇒ 375px 上根本不會開），`div` 則是鍵盤到不了。桌機的 `UTooltip` peek 是
  **加值層不是路徑**。
- 觸發鈕的 `aria-label` **必須含日期**（`備註：{YYYY/MM/DD HH:mm} {片名}`）：一張表最多 24 顆
  同樣的鈕，同一部片還會有多筆重刷，只寫片名分不出是哪一筆。
- 對話框內文用 `whitespace-pre-wrap`（還原斷行）+ `break-words`（沒有空白的長英數字串不撐破框）。
  `UModal` **不要傳 `:scrollable`**：預設值已經是 body 自己捲、標題固定。memo 的規格上限是
  2000 字（DB 的 `viewing_record_memo_check`），捲動是必要的。
- **沒有備註的那 101 筆（58%）整格留白，不畫「—」，也不放 disabled 的鈕**。一整欄的破折號會
  蓋過真正有備註的那 73 筆，而 disabled 的鈕在螢幕閱讀器上仍會被念到。

⚠️ 這裡原本有一條「門檻要跟欄寬對齊，否則程式截一次、CSS 再截一次」。**那條規則的前提隨機制
一起消失了**（現在只有長的那一支會被截），所以換成：門檻（16 字，`MEMO_INLINE_MAX`）與欄寬
（`max-w-32`＝128px，約 9 全形字）**刻意不對齊**——長的那一支交給 CSS 的 `truncate` 截一次就好
（截了一定有按鈕），短的那一支改折行所以根本不截。

⚠️ **「展開／收起用按鈕 + 展開狀態屬性」這條全站裁決本身沒有變，變的是它的實作範例。**
它原本指著這一欄，而這一欄已經不是就地展開了（`aria-expanded` 描述的是就地展開，dialog 的
觸發器該用 `aria-haspopup`）：`app/pages/app/records/index.vue` 現在是 `aria-haspopup="dialog"`
+ `:aria-label`，`aria-expanded` 一處都沒有。2026-09-08 全 repo 實查，`aria-expanded` 只剩
`LegalDocumentView.vue:55`（看歷史版本）與 `DistributionBars.vue:179`（聚合列「其他 N 家」的
展開／收合，見 §9.5 規矩 4）兩處——要找那條裁決的活範例，請去那兩個地方。
⚠️ 2026-09-14 覆查：`DistributionBars.vue` 現在**同時是兩半的活範例**——聚合列是就地展開
（展開狀態屬性），一般列是開抽屜（`aria-haspopup="dialog"`）。同一支元件上兩種手勢用兩種
屬性，正好是這條裁決要的樣子；行號則隨那一輪改動位移過一次，別再照舊行號去找。

**公開狀態**：資料是 `visibility`（enum 只有 `public`／`private`，所以是忠實的二元）。

- **預設是公開，`private` 才是例外。** 這一欄存在的價值是讓使用者一眼看出
  哪幾筆是公開的——US-29 的立場是「我的消費金額不該在我沒察覺的情況下被看到」。
- ⚠️ **不得只用顏色表達**（色盲與螢幕閱讀器拿不到）。兩態都有文字，icon 只是第二個

### 10.5 橫向捲動與固定操作欄

九欄在 375px 放不下是必然的，硬塞只會讓每一欄都斷成兩三行。所以：

- **表格在自己的容器裡橫向捲，頁面 body 永遠不橫向捲。**
- **操作欄固定在右緣**（`UTable` 的 column pinning）。David 2026-09-06 點名。

⚠️ 兩個實作陷阱，兩個都**不會有錯誤訊息**（踩雷 #185／#186）：
① 捲動容器必須是 `UTable` 自己的 root（`min-w-*` 掛在 `base`），否則 sticky 會黏在
一個自己已經被外層捲走的盒子上；② pinned 欄的預設底色是**半透明**的
`bg-default/75`，捲動時底下的欄位會透出來疊字，必須蓋成不透明。

⚠️ **1280 也橫捲，那是選的不是將就**（2026-09-06 主 session 裁決）：
中間版本為了「1280 剛好塞得下九欄」把影城欄截到 192px，長店名變成
「林口MITSUI OUTLET …」而廳別被吃掉。方向是反的——固定操作欄存在的目的正是
**讓橫捲變得可用**，為了迴避它去截掉使用者親手填的資料，而且 `SPEC` 核心價值第 2 條
正是「連版本與廳別都留得下來」。⇒ **欄寬以「不截使用者填的東西」為準。**

### 固定欄只能「疊上去」，不能「佔位」——三條路都走過了

`position: sticky` 的固定欄**沒有辦法預留自己的寬度**。內容比容器寬時，它必然蓋住
當下落在容器邊緣的那一欄；靜止（`scrollLeft = 0`）時蓋住的就是使用者**預設看到**的畫面。
2026-09-06 把三條路都實作並量過：

| 方案 | 靜止時遮蔽 | 捲到底時遮蔽 | 為什麼不是它 |
|---|---|---|---|
| ① 截欄寬讓九欄塞進 1280 | 0px | 0px | 影城的廳別被吃掉，違反 `SPEC` 價值第 2 條 |
| ② 捲動容器尾端補等寬 `padding-inline-end` | **沒有變好**：公開狀態 68px ＋ 備註 25px | — | **無效**。sticky 參照的是 scrollport 的 padding box，補 padding 只是換成蓋住別欄，而且從蓋一欄變成咬兩欄 |
| ③ 改釘**左**緣 | **0px** | 日期 47px、作品 45px | 片名會**少掉開頭幾個字而且沒有任何記號**（截尾有「…」，截頭沒有）⇒ 列的身分在捲動中消失；刪除鈕也變成每一列最左邊的東西 |
| **④ 釘右（採用）** | **備註最多 93px**（＝固定欄自身寬度） | **0px** | David 看過 ②③ 之後的選擇 |

**David 2026-09-06 的裁決：釘右。** 接受「靜止時最後一個資料欄被蓋住最多 93px」，
換取「捲動時零遮蔽」與「影城、作品一個字都不截」。

**實測數字**（1280 寬、容器 1118px）：
- 備註多的年份（2024）：表格 1323px，靜止時**備註欄 233px 中被蓋 93px**，
  加上尚未捲到的部分，畫面上只露約一個字；往右捲即可讀到，**捲到底時遮蔽 0px**。
- 備註短的年份（2026）：表格 1146px，靜止時只蓋到 28px（幾乎只有內距）。
- 375px：靜止時被蓋的是作品欄的 93px（尾端），捲到底同樣是 0px。

**2026-09-07 追記：備註欄從 `w-56`（233px 實測）收到 `w-40`（160px），而那 93px 一點都沒有變。**
很容易誤會「欄變窄 ⇒ 遮蔽變小」。不是。把上面三組實測數字反推可以得到一條規律，三組都吻合：

> **遮蔽量 = min(表格寬 − 容器寬, 固定欄寬)**，而被蓋住的是**表格座標
> `[容器寬 − 固定欄寬, 容器寬]` 這一段**（不必然是最後一個資料欄）。

1280 下容器 1118px、固定欄 93px、2024 年備註欄左緣在 997px（＝1323 − 233 − 93）。備註欄不論多寬，
靜止時露出來的都只有 `[997, 1025]` 這 28px，扣掉 `td` 的 16px 左內距後剩 **12px 字寬，不到一個字**。
要讓它整欄露出來，備註欄得窄到 28px 以內（比「備」這個字還窄）。⇒ 改窄換到的是**表格總寬
1323 → 1250（−73px）、橫捲距離 205 → 132px**，不是遮蔽變小。

**375px 的遮蔽也沒有變**：觸發鈕留在備註欄裡，固定操作欄仍然只有編輯／刪除兩顆鈕（93px），
被蓋的仍然是作品欄的 93px。⇒ 下面那條「把 93px 釘住，超過就是有人讓代價變大了」的 tripwire
**這一輪沒有被踩到**。

> | 表格寬 | 1250 | **1250** ✅ |
> | 固定操作欄寬 | 93 | **93** ✅ |
> | 1280 下被蓋的欄 | 備註 93px | **備註 93px**（欄寬 161） ✅ |
> | 375 下被蓋的欄 | 作品 93px | **作品 93px**（欄寬 289） ✅ |
> | 375 頁面橫向溢出 | 無 | **無**（375/375） ✅ |
>
> tripwire 沒有被踩到，「欄變窄不會讓遮蔽變小」那條規律三組數字全部吻合。
>
> ### 🔴 但實測同時發現一件推算沒有預見的事：**被蓋住的現在是一顆按鈕**
>
> 備註欄的長備註觸發鈕是 `block max-w-full`（外層 `max-w-32`），所以它**撐滿整欄**：
> 實測 `x = 1071..1199`（128px），而固定操作欄是 `x = 1107..1199`。
> ⇒ **那顆 128px 的鈕只有最左邊 36px 點得到**（`elementFromPoint` 在左緣回傳它自己、
> 在中心與右緣回傳「操作」欄）。
>
> 舊的權衡是「被蓋住的是**要瞄一眼的文字**」，那個代價很小；
> 現在被蓋住的是**唯一的互動入口**，代價的性質變了——這是換掉備註機制時沒有一起重算的。
>
> **David 2026-09-08 裁決：備註鈕先不動。** ⇒ **這是已知限制，不是待辦。**
> 下一棒不要「順手修掉」——修掉等於推翻這則裁決。
>
> 真的要處理時，量過的三條路是：
> (A) 備註欄縮到 68px 以內（鈕全露，但預覽文字沒了，等於退化成一顆圖示）；
> (B) **只把長備註的觸發鈕移進固定操作欄**（短備註仍留在格子裡，不動 2026-09-07 那則裁決）；
> (C) 維持現狀。當時的建議是 (B)。
>
> ⚠️ 量這一條的方法有陷阱，見踩雷 #242：`elementFromPoint()` 對**視窗外**的座標回 `null`，
> 而 null 會讓「這個點上是不是我要的元素」一律判成 false ——
> 也就是「被蓋住」與「不在視窗裡」給出同一個答案。第一次量就是這樣量的，
> **而它碰巧得到了對的結論**；捲進視窗重量才是有效的證據。

⚠️ **不要為了消滅那 93px 去截欄寬，也不要改成釘左**——兩條都被走過而且被否決了。
⚠️ **連帶**：公開狀態欄放在備註左邊。釘右的固定欄在靜止時必然蓋住最後一個資料欄，
而被蓋住的不該是「一眼掃哪幾筆是公開的」那一欄；備註本來就是
「瞄一眼、要看全文再展開」的欄位，由它來當那個位置的代價最小。

⚠️ **這一條要用會說話的斷言守住，不是用「看起來對」**（踩雷 #188）：
量「固定欄在不在視窗內」對這個問題**永遠是綠的**；要量的是
**每一個資料欄與固定欄的矩形重疊寬度**，並把 93px 這個已知值釘住——
超過就是有人讓代價變大了，變成 0px 也要看一眼（可能是有人改成了被否決的釘左）。

**這是流程的一部分，不是錯誤處理。** 帶著已輸入的片名進來，第一個欄位已經填好。

```
┌─────────────────────────┐
│ ← 新增作品               │
├─────────────────────────┤
│ 這部片還不在片庫裡。      │
│ 填一點資料就能開始記錄。  │

**視覺稿：`docs/design/mockups/film-new.html`**（亮暗兩版截圖在 `mockups/shots/`）。
上面的 ASCII 是骨架，以下是視覺稿補上的決定。

#### 即時票根預覽

表單右側（手機上是表單**上方**）放一張**跟著欄位即時變動的 `TicketCard`**。

它存在的理由只有一個，而且直接對著硬約束 (1)：
**讓人在按下按鈕之前就看到「沒有海報也是一張完整的票根」**，
而不是先想像出一個破圖、再被一句安慰的文案安撫。
這也是 §0「無海報的卡片要好到使用者不會希望它變成海報」唯一能被使用者親眼驗證的地方。

#### 兩個入口，兩種收尾

`/search` 與 `/app/records/new` 都連到這一頁，但使用者手上的東西不同。
**差別只在返回目標與按鈕文案，表單本身完全一樣。**

| 從哪裡來 | 頂端返回 | 主要動作 | 按下之後 |
|---|---|---|---|
| `/app/records/new`（手上有一筆記到一半的紀錄） | ← 回到記錄 | 建立並繼續記錄 | 回 `/app/records/new`，這部片已選好，**其餘欄位原樣還在** |
| `/search`（只是在找片，手上沒有紀錄） | ← 回到搜尋 | 建立並記一場 | 去 `/app/records/new`，這部片已選好 |

⚠️ **未登入從 `/search` 進來**：導到登入並帶 `?next=`，登入後**直接回到這一頁且片名還在**。
把人丟回搜尋首頁等於要他重打一次，而他本來就是因為找不到才走到這裡的。

⚠️ **這個路由目前不存在，而兩個入口都已經連過來了**（2026-09-06 主 session 回報），
所以現況是兩個入口都 404——正好落在硬約束 (1) 最不能壞的那條路上。

#### 欄位

- 只有中文片名必填。其餘全部選填——**擋住人比資料不完整更糟**。
  US-14 寫的是「只需填片名與年份」，但**連年份都不該擋**：缺的欄位之後比對到 TMDB 會自己補（US-18）。
- 空欄位在票根卡上**就是不存在**，不渲染「—」或「未知」佔位（同 §4.3 的票價規則）。
- 必填未填時：主要動作停用，錯誤顯示在欄位旁邊，不在頁面頂端。

#### 海報四態（不是三態）

原本只寫了三態，漏掉最重要的第一態：

1. **沒有海報** — 這是預設，**也是完成態**。海報欄不存在，卡片自然變寬，不留灰色佔位、不畫破圖圖示。
2. **上傳中** — 結構性骨架 + 進度，不用轉圈（§10）。可取消。
3. **待審核** — 小標記「審核中」+ 一句「只有你看得到」。
4. **被拒** — 說發生了什麼與怎麼修，不道歉（§8）。
   **「就這樣不放海報」必須是一個真的、並列的選項**，不是放棄。

`ugc-poster` 是 private bucket 走 signed URL。

⚠️ **上傳區跟文字欄位同一種待遇**（同底色、同邊框），不要做成整份表單裡最重的一塊——
它是選填的，加重它會把注意力從唯一的必填欄拉走。也不要虛線框：那是 SaaS 預設，而且會讀成「這裡是空的」。

#### 已比對到 TMDB 的作品

`SPEC` 明寫**禁止上傳海報**（無必要，只增加曝險）。
**做法是那一欄根本不出現，不是出現一個停用的欄位。**
停用欄位等於公告「這裡本來有東西」，然後逼使用者去想為什麼不能用。

## 12. `/app/settings` 票價隱私（SPA，US-29/30）

**硬約束 (2)。這一頁是全站最需要小心的地方。**

`show_cost` 是一個**全域、預設 false、一翻就追溯套用全部歷史**的布林。翻開它，David 過去 169 筆紀錄的票價、共 NT$5x,xxx 的消費，全部變成公開。

**所以它不能是設定清單裡的一個 `USwitch`。**

```
┌──────────────────────────────────────────────────┐
│  票價                                            │
│                                                  │
│  你的票價現在只有你看得到。                       │
│                                                  │
│  公開之後，任何人打開 /u/clipwww 都會看到你       │
│  169 筆紀錄的每一筆票價，以及年度總花費。         │
│  這會套用到你過去所有的紀錄，不只是之後新增的。   │
│                                                  │
│  ┌────────────────────────────────────────────┐ │
│  │ 別人會看到的樣子                            │ │
│  │ ┌────┬──────────────────────────────────┐  │ │
│  │ │ 26 │ 劇場版 吉伊卡哇 人魚島的秘密       │  │ │
│  │ │ 六 │ 林口威秀 2D 16:00 2張 NT$520      │  │ │
│  │ └────┴──────────────────────────────────┘  │ │
│  │        2026 年花了 NT$3,120                 │ │
│  └────────────────────────────────────────────┘ │
│                                                  │
│              [ 公開票價 ]                        │
│                                                  │
│  隨時可以關掉。關掉之後別人就看不到了。           │
└──────────────────────────────────────────────────┘
```

四條規則：

1. **記錄 ≠ 公開。** 表單永遠可以填票價，這個開關只管**發佈**。要在文案上講清楚，否則使用者會以為關著就不能記帳。
2. **翻之前必須看到後果。** 上面那個預覽區用**使用者自己的真實紀錄**渲染，不是示意圖。

4. **隱藏時不留佔位。** 票價是 meta 行最後一項，被擋掉時那一行就是短一截。**絕不渲染 `NT$ ———`**——那等於公告「這裡有一個價格」，反而洩漏了「這個人有記帳」。

### 12.1 NT$0 不等於隱藏

實測 169 筆裡 **16 筆 `cost` 為 0**（兌點票、免費場）。它們必須跟「已隱藏」在視覺上完全不同：

- `cost = 0` → 顯示「**免費**」（或依 memo 顯示「兌換」）
- `cost` 被 RLS 擋掉 → 該欄**不存在**
- `cost` 為 NULL（沒填） → 該欄**不存在**

後兩者長得一樣是可以接受的，因為外人本來就不該分辨得出「沒填」與「不給看」。

### 12.2 這一頁的其他項目

username 改名（US-24，改名後舊網址 301）、匯出（US-46）、刪除帳號（US-47，`UModal` + 打字確認）。**票價區塊獨立在最上方，跟其他項目之間有明顯的視覺分隔**——它不該混在一排開關裡。

> 代價是 David 最常走的那條路多了一次點擊。

### 14.1 `/admin` 的 TMDB 快取維護區

這一區有兩顆會真的動資料的按鈕（refresh / purge），所以**文案就是功能的一部分**——
下面四條不是修辭偏好，是「寫錯就沒有人敢按、或按了誤以為壞掉」的地方：

- **(a) 進頁面就看得到現況，不是按了才知道。** 至少三個數字：「到期待刷新 N / 追蹤中 M 列」、
  「到期待清除 K 列」、「最後一次有快照被更新」。
  ⚠️ 最後那一個**不是**「排程上次執行的時間」——某一輪跑到沒有列到期時它什麼都不會寫。
- **(b) ★ `abortedBy === 'budget'` 顯示成資訊，不是錯誤。** 它是正常的收尾方式（推進到時間預算
  上限，沒做完的列還在佇列裡），畫成錯誤會讓管理者不敢再按，而這個功能的用法就是
  「按不完再按」。`'throttle'` 顯示成警告並明說現在不要再按；**只有 `'fatal'` 是錯誤**
  （設定層的錯，例如金鑰不對）。
- **(c) errors 必須標明「取樣，最多 5 筆」。** 失敗 200 列而畫面只列 5 條時，不講的話那 5 條
  會被讀成全部。
- **(d) purge 區塊必須寫「沒按這顆按鈕不會違規」。** 合規靠讀取端逐列把關（過期欄位直接變空值、
  退回文字卡片），不靠這一步；這顆按鈕做的是另一件事——不要在資料庫裡留著已經沒有權利保存的內容。
  少了這一句，管理者會把它讀成「沒按＝違規中」。

⚠️ **待決（見 §18 第 5 條）：** `-AdminShell.vue` 的分頁列只有三格，進了佇列之後**沒有回到
`/admin` 的入口**（回去的路是 `AppNav` 的「管理後台」）。要不要補第四格，待 David 決定。
這是 2026-09-07 那一輪造成的可用性缺口，是已知取捨，不是疏漏。

**這不是禮貌頁面。** 三件事讓它變成功能而不是裝飾：

1. **政府資料開放授權條款第 1 版：「未盡顯名標示義務者，視為自始未取得授權。」**
   顯名標示做不到位，不是少了一行小字——是全站 2,669 部作品與 107 家影城的授權**自始不存在**。
2. **著作權法 §90-7 的免責，前提在 §90-4，而那些機制必須在侵權發生時「已經建置」。**
   事後補做不能回溯適用。這是整個產品裡唯一「晚做就永遠補不回來」的東西。
3. **海報顯示不得置於付費牆之後**（§90-7 第 2 款：未直接自侵權行為獲有財產上利益）。
   連帶地，**這四頁本身也不得要求登入、不得放在任何牆後**。

### 15.0 四個路由，但只有三個是文件

| 路由 | 是什麼 | 資料來源 |
|---|---|---|
| `/legal/terms` | 文件 | `legal_document` where `kind='terms'` |
| `/legal/privacy` | 文件 | `kind='privacy'` |
| `/legal/copyright` | 文件（**且是顯名標示的正式落點**） | `kind='copyright_policy'` |
| `/legal/dmca` | **表單，不是文件** | 寫入 `takedown_notice` |

⚠️ `legal_doc_kind` 這個 enum 只有三個值（`terms` / `privacy` / `copyright_policy`），
**沒有 `dmca`**。這不是遺漏：`/legal/dmca` 是一個受理表單，不是一份要簽署的文件。
不要為了「四頁一致」去幫它生一份文件，也不要把它做成「文件 + 底下一個表單」——
著作權人來到這一頁只有一個目的，讓他先讀完一份條款再填表是在增加放棄率。

**視覺稿：`docs/design/mockups/legal.html`**（亮暗兩版截圖在 `shots/`）。
四頁的版面、匿名侵權通知表單、送出後與回復通知的呈現都在那裡；
頁尾的顯名區同時是 `DESIGN_SYSTEM §9.1` 份量規則的落點（`data-brand` 屬性已就位）。

### 15.1 三份文件頁的共同版面

```
┌──────────────────────────────────────────────────────┐
│  服務條款                                             │
│  v1.2 · 2026-03-01 生效 · 看歷史版本                   │
├───────────────┬──────────────────────────────────────┤
│ 目錄（sticky） │  1. 我們提供什麼                      │
│  1 我們提供什麼│  ……內文 34ch……                      │
│  2 你的內容    │                                      │
│  3 著作權      │  2. 你的內容                          │
│  4 三振與終止  │  ……                                  │
│  5 終止與退出  │                                      │
└───────────────┴──────────────────────────────────────┘
│  AttributionFooter（每一個公開頁都有，DS §9）           │
└──────────────────────────────────────────────────────┘
```

- **版本與生效日必須顯示在標題正下方。** `legal_acceptance` 是綁 `document_id` 記的，
  使用者同意的是**某一版**；畫面上看不到版本，那筆同意紀錄對使用者就是不可查證的。
- **歷史版本要查得到。** `legal_document` 是 `unique(kind, version)`，舊版留著就是為了舉證。
  入口放在版本號旁邊，不必做成顯眼的功能。
- **條號要能深連結**（`#s4` 之類）。侵權通知、客服回覆、admin 備註都會需要指向特定一條。
- **目錄**：桌機左側 sticky；手機收在標題下的一個可展開區塊，預設收合。
  法律文件的閱讀行為是掃讀與跳讀，不是從頭讀到尾。
- 內文行長維持 `34ch`（DS §2.4），標題階層**只到 h3**。
- ⚠️ **不要用 Nuxt UI 的 prose 預設樣式。** 那是為技術文件調的，字級與行高跟本站的紙不同調，
  而且會把 `<code>` 渲染成等寬字——DS §0 明確排除等寬字當資料微標籤。

### 15.2 `/legal/copyright` 額外承載的東西

這一頁是**顯名標示的正式落點**，`AttributionFooter` 只是每頁的縮寫版，全文在這裡。必須包含：

- **政府開放資料顯名聲明**，資料集全名要寫全：文化部影視及流行音樂產業局
  「電影片分級及相關資訊」、「全國電影院資料」。
- **TMDB 聲明**：`This product uses the TMDB API but is not endorsed or certified by TMDB.`
  \+ TMDB logo，**視覺份量小於本站字標**（TMDB 條款要求）。
- **海報政策**：有 TMDB 的熱連結不轉存、UGC 的使用者上傳、已比對到 TMDB 的禁止上傳。
  用一個三列的表講完，因為使用者真正會問的是「我上傳的圖去哪了」。
- **三振條款**：必須寫明「三次涉有侵權情事應終止全部或部分服務」（§90-4 的要件），
  並且**連到使用者自己的三振狀態**（見 §15.5）。條款寫了但使用者查不到自己有幾次，
  第三次就是突襲。
- **受理窗口**：只有 `/legal/dmca` 那張表單，一段話加一顆按鈕。**不公告任何電子郵件**（📌 2026-09-07 David 裁決）。
  - 原本這裡要的是「`copyright@` 的信箱，以及一句『或用表單，會快一點』」，那個規格的著眼點是
    「多一個管道比較保險」——**在有人收得到信的前提下它是對的**，所以寄信能力上線後可以回來重新考慮。
  - 推翻它的是兩件當時不知道的事實：① 本專案沒有任何寄信能力（寄信服務 2026-09-06 裁定擱置到上線前）；
    ② `filmnote.tw` 於 2026-09-07 對 8.8.8.8 實測是 NXDOMAIN（查無 NS/A/MX/SOA），公告出去的位址
    寄過去必退信。兩者相加，那個「保險」的管道是**負值**——它跟隱私權政策寫「你隨時可以刪除帳號」
    但沒有實作是同一類錯誤。
  - 這一節只剩一段文字加一顆按鈕是**刻意的**，不是還沒寫完。要加第二個管道之前，先確認那個管道
    真的有人收得到。

### 15.3 `/legal/dmca` 侵權通知表單

**未登入可提交。** 著作權人幾乎不會是我們的使用者，要求註冊等於關掉這個窗口，
而窗口沒開就不符 §90-4 第 3 款。

欄位與 `takedown_notice` 一對一：

| 畫面欄位 | 欄位 | 必填 | 備註 |
|---|---|---|---|
| 你的姓名／單位 | `claimant_name` | ✔ | |
| 電子郵件 | `claimant_email` | ✔ | 受理確認信會寄到這裡 |
| 電話 | `claimant_phone` | | |
| 你主張被侵權的著作 | `work_description` | ✔ | 多行；提示要寫到「能辨識是哪一個著作」 |
| 侵權內容的網址 | `target_url` | ✔ | 見下方的回顯 |
| 善意聲明 | `statement_good_faith` | ✔ | 勾選 + **聲明全文就寫在勾選框旁邊** |

- **`target_url` 貼上後要解析並回顯「你指的是這一筆嗎？」**，用一張唯讀的票根卡呈現。
  兩個作用：(a) 讓 `target_film_id` / `target_record_id` 真的被填進去，admin 才不必自己找；
  (b) 大幅減少誤報——很多誤報是網址貼錯。解析不到就讓它留空並照常收件，不要擋。
- **善意聲明不可以縮成「我同意」三個字。** 它是 §90-6 的要件，必須讓填的人真的讀到自己在聲明什麼。
- ⚠️ **「送出後你在這個網站上讀不到自己送過什麼」必須寫在表單最上面，不是送出後才說。**
  這張表只寫入、不提供查詢（沒有 SELECT policy），因為任何查詢介面都等於揭露
  「哪些內容被通知過、屬於誰」。**這件事會改變使用者怎麼填信箱**——
  信箱是我們唯一能回覆的管道，事後才講就來不及了。
  所以電子郵件欄位要帶一句「這是我們唯一能回覆你的方式，送出後不能改」。
- **送出後**：顯示**受理編號**（就是 `takedown_notice.id`）與「我們會寄一封確認信到 <email>」，
  並明說「這一頁重新整理之後就找不到了，請留存編號」。
  ⚠️ **不做公開的進度查詢頁。** 用編號就能查等於揭露「哪些內容被通知過、屬於誰」，
  那是另一個外洩面。後續一律走 email。
- **防濫用**：用 rate limit（同 IP／同 email）加上 email 驗證，**不要用 CAPTCHA 擋死**。
  這個窗口的使用者是法務或權利人，操作失敗率比一般使用者高，擋掉他們的代價是法遵要件失效。
- 這一頁**不得要求登入、不得放在任何牆後**，且要能被搜尋引擎索引——找得到才叫「公告窗口」。

### 15.4 回復通知（counter-notice）— 使用者端

`/legal/dmca/counter/[noticeId]`，**需登入且必須是該內容的擁有者**。

**入口不在這一頁，在內容被取下的地方**（§16 的降級態：票根卡保留位置、內容換成
「這筆紀錄因著作權通知已移除」+ 申訴連結）。人是在自己的紀錄頁上發現東西不見的，
不會想到要去 `/legal` 找申訴。

- 欄位對 `counter_notice`：`reason`（多行，必填）。
- **提交後必須顯示兩個法定日期，而且是直接讀 DB 算好的值**：

| 顯示 | 欄位 | 意義 |
|---|---|---|
| 對方要在 **{date}** 前提出訴訟證明 | `litigation_deadline_at` | 送出後 10 個工作日 |
| 否則你的內容會在 **{date}** 前回復 | `restore_deadline_at` | 送出後 14 個工作日 |

⚠️ 這兩個值由 `counter_notice_deadlines()` trigger 算（`business_days_after`），
**UI 只負責顯示，絕不在前端自己再算一次工作日**。兩邊各算一次就是兩個會分岔的答案，
而分岔的那一個會出現在法定期限上。

- 使用者最在意的問題只有一個：**「我的東西什麼時候會回來」**。這兩個日期就是答案，
  要放在畫面最上面，不是塞在流程說明的最後一段。
- `notice_status` 有七態，但**使用者端只需要看到四個**：
  已移除（`actioned`）／已提出回復通知（`counter_received`）／已轉送對方（`counter_forwarded`）／已回復（`restored`）。
  `received`、`rejected`、`litigation_notified` 是 admin 的內部狀態，不要洩漏給使用者
  ——尤其 `rejected`，那代表有人通知過但我們沒受理，內容根本沒動過，講出來只會製造焦慮。

### 15.5 使用者看得到自己的三振狀態

放在 **`/app/settings` 的帳號區塊**，不是藏在 `/legal`。

- 資料來自 `profile_private.strike_count` 與 `service_status`（`active` / `limited` / `terminated`）。
- `strike_count = 0` 時**整個區塊不出現**。沒有事的人不需要被提醒有三振制度。
- ≥1 時顯示次數、每一次對應的內容與日期，以及「還有幾次會終止服務」。
- 文案照 DS §8：說發生了什麼跟怎麼修，不道歉、不模糊。
- ⚠️ `admin_restore()` 會把該次通知造成的三振 `revoked_at` 掉，`strike_count` 由 trigger 重算。
  **畫面要跟著回到正確的數字**，不要快取一個舊的計數——使用者在意的正是「我申訴成功了沒」。

### 15.6 這一節怎麼驗收

- 四個路由**未登入**可達、回 200、不在任何牆後，且 `/legal/dmca` 可被索引。
- `AttributionFooter` 出現在**每一個公開頁**（不是只有首頁），TMDB logo 份量小於本站字標。
- 被取下的內容：票根卡**保留位置**、有申訴連結、**不整筆消失**。
- 回復通知送出後畫面上的兩個日期，與 DB 的 `litigation_deadline_at` / `restore_deadline_at` **逐字相同**。
- `strike_count = 0` 的帳號，`/app/settings` 看不到三振區塊。

## 16. OG 分享圖（跨路由）

**視覺稿：`docs/design/mockups/og.html`**（六種版面 1200×630 實尺寸，截圖 `shots/og.png`）。
中文字型那題的完整推導與實測數字在 `DESIGN_SYSTEM §2.7`，這裡只講版面與行為。

**為什麼它比看起來重要**：`SPEC` 把社群功能列為 Out of Scope，
所以**分享出去的那張圖是這個產品唯一的傳播管道**（US-32、US-33）。
它同時是政府開放資料與 TMDB 顯名義務的落點之一（`DS §9`），而顯名未盡者「視為自始未取得授權」。

### 16.1 共同結構

```
┌──┬──────────────────────────────────────────┐
│▌ │  2026 / 07 / 26（六）16:00                │  ← kicker（日期／年份／國別）
│▌ │                                          │
│▌ │  劇場版 吉伊卡哇 人魚島的秘密              │  ← 英雄，最多兩行後截斷

│▌ │  影記  clipwww          片名資料：… · TMDB │  ← 顯名列，每一張都有
└──┴──────────────────────────────────────────┘

```

- **固定用亮色的紙，不跟隨檢視者的主題。** 它是一張 PNG，沒有主題可跟；而且票根本來就是紙。
- **細內框 + 左側琥珀撕線帶**是六種版面共用的識別，讓分享圖一眼認得出跟站上是同一個物件。
- **顯名列每一張都有**，不是只有作品頁。
- meta 用 `DS §4.3` 的兩段式（影城自成不可切開的單位）。
  **在 OG 圖上這條比在站上更重要**——這裡沒有 hover、沒有捲動、沒有第二次機會。
- 字級要照「被縮到 500px 寬看」來設：英雄 72px、meta 34px、顯名列 19px。

### 16.2 六種版面

| # | 路由 | 英雄 | 備註 |
|---|---|---|---|
| ① | `/u/[username]/records/[id]` | 中文片名 | 主力。US-32 |
| ② | `/u/[username]` | `169 場` + **YearStrip** | 見下 |
| ③ | `/u/[username]/[year]` | `18 場　23 張票` | |
| ④ | `/film/[slug]` | 中文片名 | 分級章用 `§1.4` 的實色方塊 |
| ⑤ | `/venue/[id]` | 影城名 | 顯名列換成「全國電影院資料」 |
| ⑥ | 站台通用／**缺字降級態** | `一張票根` | 見 16.4 |

⚠️ **版面②把 YearStrip 放進 OG 圖，是刻意的**：它是全站簽名，
而且**零字型成本**——格子是方塊、年份是拉丁數字。
等於用一個完全不需要中文的元素同時承擔辨識度與「看得見自己的軌跡」這個價值主張。

### 16.3 三件永遠不畫

| 不畫 | 為什麼 |
|---|---|
| **票價** | 爬蟲是 anon 身分，不論 `show_cost` 都不畫 |
| **原文片名** | 實測 **344 / 2,669（12.9%）**含 Noto Sans TC 畫不出來的字。八分之一的機率出現豆腐格，不值得換那一行附註 |
| **備註** | 字型不可預測只是其一；更重要的是 OG 圖公開、給陌生人看、會被搜尋引擎索引，**備註是私人內容** |

⚠️ 另外兩條沿用既有決定：**無海報的作品就是純票根版面，不放灰色佔位圖**；
以及 `BUILD_PLAN` 的「**不要把 TMDB 海報 pipe 進自己的生成器**」——那等同轉存。
OG 圖只用純文字票根版面。

### 16.4 缺字降級態

渲染前拿標題的碼位比對預先算好的 cmap 集合（`DS §2.7`）。有缺字就**換掉片名那一行**
（`一張票根`），日期／影城／場次／顯名列**全部保留**——資訊量幾乎沒少。

> **絕不渲染豆腐格。** 一個破格子讀起來是「這站壞了」，
> 而 OG 圖唯一的工作就是讓人覺得值得點進來。

實測命中率：**2,669 部中文片名裡 5 部（0.2%）**。其中 `Ｎ妠刉x鬼` 是**來源資料本身壞掉**，
不是字型問題——**這一筆值得回報 backend**，修掉之後降級態就只剩 4 部。

### 16.5 驗收

- 六種版面各產一張，**放到 1200×630 的一半（600×315）看**，英雄仍然讀得清楚。
- 隨機抽 20 部作品產圖，**數有幾張出現豆腐格**（應為 0；命中降級態的應顯示「一張票根」）。
- 每一張都有顯名列，且 TMDB 標記的視覺份量小於「影記」字標。
- 任一張都不得出現票價、原文片名、備註。
- **OG 路由跑在 Node runtime**（Edge 放不下 6.76 MB 的字型，見 `DS §2.7`）。

## 17. 錯誤與降級態

| 狀態 | 設計 |
|---|---|
| 改名後的舊網址 | Nitro middleware 301，**使用者看不到中間頁**。但若舊名已被回收，落到 404 要說「這個名稱的主人改名了」而不是「找不到頁面」 |
| 被下架的紀錄（`moderation_state`） | 票根卡保留位置，內容替換成「這筆紀錄因著作權通知已移除」+ 申訴連結。**不要整筆消失**——那會讓作者以為資料掉了 |
| 已終止服務的帳號 | 公開頁回 404，不列入 sitemap |
| TMDB 快取逾期 | `film_public` view 會用 `expires_at > now()` 把 TMDB 欄位變成 NULL，作品**自動退回票根卡**。這是設計好的路徑，不是錯誤——所以票根卡必須夠好看 |
| 圖表載入失敗 | 顯示資料表 fallback，不顯示破圖 |
| 離線／送出失敗 | 表單內容留在 `sessionStorage` |
