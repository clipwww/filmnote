剩餘工作日是列表的排序鍵，也是列表裡最醒目的東西。 這個佇列跟另外兩個的差別在於：漏掉一筆的後果是法律責任，不是資料品質。 所以不按受理時間排，按剩餘時間排；快到期的用紅色 chip，而且紅色只用在這裡。
⚠️ 所有日期都讀 DB 算好的值（counter_notice_deadlines() trigger 用 business_days_after 算），前端絕不自己算工作日—— 兩邊各算一次就是兩個會分岔的答案，而分岔的那個會出現在法定期限上。
⚠️ 「已轉送使用者」是手動勾的，不能自動填。 寄出通知是站外行為，程式無從得知它真的發生過（0006 migration 的註解寫得很清楚）。 自動填只會產生一個看起來已履行、實際沒有的紀錄，而那正是日後要拿來舉證的欄位。 介面上要讓它看起來像一個「我確認我寄了」的動作，不是一個狀態顯示。

⚠️ 這份稿裡的紅色是佔位

破壞性動作用的紅（#B3261E / 暗色 #F2B8B5）是這份稿自己挑的， 實作要用 Nuxt UI 的 error 語意色（DS §1.5： error/success/warning/info 沿用 Nuxt UI 預設，只用於表單驗證與 toast）。
⚠️ 但 DS §1.5 同時警告：Nuxt UI 的 warning 預設就是 amber， 在暖底上會跟 primary 撞。admin 的三個佇列裡不要同時出現 primary 與 warning，要提醒就用 error 或改用文案。

④ /admin/reports — 片名／影城錯誤回報（US-49/50）

同一套左列表右詳情，內容最單純：誰、回報哪一筆、說哪裡錯了、目前的值是什麼。 兩顆鈕：照著改／不改，回覆理由。
⚠️ 「照著改」不可以直接寫進政府核准片名的欄位。那個欄位的權威來源是影視局開放資料， 被人工覆蓋之後下次資料更新會打架。修正要進覆蓋層，不是進來源層。
