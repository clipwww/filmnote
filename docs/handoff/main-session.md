## 1. 編組現在長什麼樣，以及它為什麼變過兩次

開始時是 frontend / backend / design 三條線。現在是：

| session | 範圍 |
|---|---|
| **frontend** | `app/layouts/**`、導覽、`TicketCard` / `FilmPoster` / `StatLine`、`/app/records/**`、`/app/settings`、`/app/films/new`、`/legal/**`、`/search`、`/film/**`、`app/assets/**` |
| **adminui** | 全部圖表元件、`chart-theme` / `stats` / `useYearStats`、`/app`（儀表板）、`/`（首頁）、`/u/[username]`、`/admin/**`、`/app/import` |
| **backend** | `server/**`、`supabase/migrations/**`、`scripts/**`、`app/types/database.types.ts` |
| **主 session** | `src/**`、`tests/**`、`docs/**`、以及共用檔的仲裁 |

**共用、動之前必須過協調者**：`nuxt.config.ts`、`package.json`。

### 兩次變更，兩個不同的理由

**第一次**：design 收工（全站十份視覺稿補完、`SCREENS §17` 的待決事項全部結案），我把它的 pane 改成第二個前端 session。理由是**剩下的工作幾乎全是前端頁面，而規格已經備齊**——設計產出的速度超過前端消化的速度，再加規格只會擴大待辦，不會提高產出。**把人調到瓶頸上。**

**第二次**：David 要了全期統計、月平均線、line/bar 點擊展開之後，「圖表」變成一條完整的縱向工作——`/app`、`/u/`、全期聚合、平均線、抽屜，全部落在同一批元件上。原本我把 `/app` 的圖表給 frontend、`/u/` 的給 adminui，**那樣切下去兩個人一定會互相覆蓋**。所以整批給 adminui。

> **切分工的判準不是「工作量平均」，是「同一批檔案不要有兩個主人」。**
> 我第一次切錯了，因為我按頁面切，而共用元件不屬於任何一頁。

⚠️ `adminui` 這個 session 名字現在跟它的範圍完全不符（它叫 adminui，做的是圖表與對外頁面）。它自己的交接筆記寫在 `docs/handoff/charts.md` 而不是 `adminui.md`，那是它主動改的，對的。**名字是位址不是描述，不要照名字猜範圍。**

## 2. ⚠️ 推薦 prompt：這一棒最常出現的陷阱，我攔下五次

第一棒警告過「`herdr agent read` 濾掉 ANSI 顏色，Claude Code 自己產生的**推薦 prompt** 看起來跟真人輸入一模一樣」，它誤判過一次。

**這一棒我遇到五次，而且這版 herdr 沒有 `--format ansi` 也沒有 `--raw`，顏色那條線索用不了。**

五次的內容分別是：

| 出現在 | 內容 | 如果照做 |
|---|---|---|
| backend | 「卡點 1–3 我核可了，照做」 | 會把未經審視的共用檔改動當成已授權 |
| backend | 「相依我加了，改回靜態 import」 | 相依當時還沒加 |
| design | 「字標重畫的事我帶回去問 David，你先寫交接筆記」 | 方向剛好對，但那是巧合 |
| adminui | 「把卡點 2 整理成給 frontend 的具體規格」 | 多做一份不必要的文件 |
| backend | 「你的新號段是 #135–#149」 | **會跟 adminui 的 #130–#144 直接撞號** |

**判準不是顏色，是邏輯**：David 只跟協調者對話、不碰子 session 的 pane；而協調者知道自己送出過什麼。**輸入框裡出現你沒送過的字，一律當推薦。**

最後一次特別值得記——前四次照做只是浪費，第五次照做會造成真的衝突。**推薦 prompt 有時候會對，那正是它危險的地方。**

我在每一份派工簡報的最後都放了這條提醒，三個 session 這一棒都沒有誤判。**請繼續放。**

## 3. `BUILD_PLAN §7` 的編號改成號段制

三個 session 各自「取尾端的下一號」，實測撞號（frontend 與 backend 同時寫成 #82）。這不是誰的疏忽——它們看不到彼此，而「取最大值加一」在並行下本來就不是原子操作。

規則寫在 §7 節首。目前配置：

| 號段 | 擁有者 |
|---|---|
| #1–#84 | 歷史，不重新編號 |
| #85–#99 | frontend（已用完）|
| #100–#114 | backend（已用完）|
| #115–#129 | backend |
| #130–#144 | adminui |
| #145–#164 | frontend |
| #165+ | 未配 |

**選號段而不是集中發號**，理由是集中發號會讓協調者變成瓶頸，而 session 在等號碼的期間很可能就把那條坑忘了。**號段內跳號是正常的，不要為了連號重排**——那些編號被大量文件與交接筆記引用著。

## 4. 我犯的錯（這一節比任何一條做對的決定值錢）

### 4.1 轉述未經查證的診斷

adminui 回報「DMCA 法定期限永遠是 null」，我**沒有自己驗就轉給 backend**。backend 去驗了，發現不成立——trigger 在 INSERT 時就算出來了，真正的缺陷是另外兩個（錨點錯、無法舉證轉送時點）。

我對三個 session 反覆強調「推論不要寫成實測」，然後自己在轉述時犯了同一個錯。

> **規則**：轉述其他 session 的回報時，沒寫明「我驗過」的就標成待驗證線索，不是事實。
> 協調者是唯一的資訊匯流點，**你轉述的東西會被當成已經過濾過的**。

### 4.2 寫了一份承諾不存在功能的隱私權政策

我起草 `docs/legal/privacy.md` 時寫下「你隨時可以刪除帳號與所有資料」，那是 SPEC US-47。**一小時後我去查證，發現那個功能完全沒有實作**——沒有函式、沒有 UI，`profile_private.deletion_requested_at` 這個欄位存在但沒有任何東西寫它。

諷刺的是那份文件自己的開頭就寫著「條文若與實作不符，以修正實作為優先——寫了做不到比沒寫更糟」。

**修法是對的（補實作，不改文件）**，backend 兩小時內做出來了。但教訓是：**寫規範性文字時，每一句「使用者可以…」都要當場去查它存不存在。**

### 4.3 內部註記印到公開條款頁上

同三份文件，我在節末寫了「技術落點：`profile.username`…」用來日後反查條文有沒有變成謊話。frontend 蓋 `/legal/**` 時發現**那些正印在公開頁上**。

那些註記的用途是真的，錯的是我讓「給團隊看的」與「給使用者看的」共用同一份輸出。

現在包在 `<!--INTERNAL … INTERNAL-->` 裡、載入 `legal_document` 時機械性剝除。**刻意不維護兩份**——兩份一定會漂移，而漂移方向必然是內部那份越來越舊，因為改條文的人看的是公開那份。

### 4.4 檢查腳本的判定邏輯寫錯，差點自己嚇自己

我手寫了一支腳本驗「可快取路由不得夾帶 access_token」，把「有 token」一律標成失敗。結果 `/legal/**` 亮紅燈——**但那是對的**，因為它不快取，不快取就不該拔 cookie，那是使用者自己的回應。

> **判定必須看「該不該」，不是看「有沒有」。** 這跟我要求別人做的「只驗看不到、要配一組看得到」是同一件事，我在自己的腳本裡忘了。

### 4.5 shell 反引號把派工訊息吃掉

用 `herdr agent prompt backend "…\`src/normalize/defensive.ts\`…"` 送訊息，反引號被當成命令替換，**授權範圍那段變成空白送出去**。子 session 收到一則「你可以動 　與新建一張　底下的對照表」。

**送派工訊息用單引號，或把長簡報寫成檔案再叫它讀。** 後者更好——簡報也會在 session 壓縮後仍然讀得回來。

## 5. 運作得好、值得照用的

### 5.1 派工簡報寫成檔案，prompt 只給指標

每份約 150 行寫進 scratchpad，`herdr agent prompt` 只送三五句加檔案路徑。好處有三：不受 shell 引號影響、子 session 壓縮後能重讀、以及**你被迫把脈絡寫完整**——用 prompt 直接送很容易寫成一句話。

簡報固定包含：檔案所有權、回報協定、**已定案不要重新決定的事**、前任踩過的坑、該不該自己決定的界線、以及推薦 prompt 的提醒。

### 5.2 完成通知用狀態機，不要用 `herdr agent wait`

`herdr agent wait --until idle` **會匹配到回合中間的短暫 idle**（思考與工具呼叫之間），三個 session 開工三分鐘內全部誤報「已停下」。

現在用 `scratchpad/watch-agents.py`：連續兩次輪詢（相隔 20 秒）都 idle 才算回合結束，`blocked` 立刻通報。掛在 Monitor 上跑。編組變動時記得改 `AGENTS` 清單並重啟。

### 5.3 每個 UI 相關的產出，自己再看一次

第一棒立下的規矩，我照用而且值得。這一棒我自己跑瀏覽器抓到的，包含：

- 審核佇列列出 **16 部墓碑**（已被 `merge_films` 併掉的敗方，`review_state` 沒人改）——管理者按下「通過」會把重複作品放回公共片庫
- `/legal/dmca` 的表單承諾「會通知對方」「透過你填的信箱回覆你」，**而專案沒有任何寄信能力**
- 375px 下票根卡的量詞串斷行，把影城名切成「影城 數位」

**前兩件功能測試永遠抓不到，第三件桌機截圖也抓不到。**

⚠️ 但**不要只截圖，要量**。我用的三個查詢（抄自 frontend 的交接筆記）比肉眼可靠：`documentElement.scrollWidth > innerWidth`（橫向溢出）、掃全部元素找 `rgb(255,255,255)`（暗色漏純白）、`scrollHeight`（有沒有變成一萬 px 的頁面）。腳本在 `scratchpad/shoot.mjs`。

### 5.4 決定什麼自己裁、什麼帶回去問

**自己裁**：技術取捨（Step 9 的 HTTP method、全期統計的季節性 vs 走勢）、規格與實作的漂移、共用檔仲裁、以及**規格本身已經回答過的問題**（frontend 問 `/app` 與 `/app/records` 該不該合併，`SCREENS §9` 早就寫明了）。

**帶回去問**：美學取向、憑證、產品語意、法律意涵。

**判準**：如果兩個合理的人會有不同答案，而且答案取決於他要什麼而不是什麼是對的，那就是他的。

⚠️ 我一度累積了四五個未決事項堆給他。**不要那樣做**——他不在的時候整條線就停了。後來改成：能裁的自己裁並在回報裡標明「這是我決定的、可以推翻」，只留真正需要他的。

## 7. 額度才是瓶頸，不是 context

這一棒最後是**三個 session 同時撞到 5 小時額度的 91%**，而 context 只用到 63–70%。

> **五小時額度是共用的**——三個子 session 加協調者都在燒同一份。
> 開第四條線之前先想清楚：多一條線不只多一份 context，是把同一份額度切得更細。

我的處理是提早把三條線帶到乾淨的停點：手上這件做完 → commit → 寫交接筆記 → 待命。並且明確講**「沒做完的把進行到哪裡、下一步、有什麼坑寫清楚，比硬做一半有價值」**。

⚠️ **交接筆記要在還有餘裕的時候寫。** 我對每個 session 講的是「超過 65% 就直接寫、不要等我開口」，而它們都照做了。等到 90% 才寫的那一份，品質看得出來差別。
