# 註解慣例

2026-09-20 立。當時全專案 **7,758 行註解 / 27,395 行（28%）**，
最極端的檔案 74% 是註解。

## 規則

1. **每則 ≤3 行。** 壓不下去的搬進 `docs/`，程式裡留一行指標。
2. **寫「為什麼」與「改了會怎樣」，不寫「這段在做什麼」**——後者程式自己會說。
3. **不寫誰要求的、原話是什麼。** 留結果與理由就夠；日期可以留（`2026-09-20 改成…`）。
4. **重複的一律刪。** 複述 `BUILD_PLAN §7`／`SCREENS`／`DESIGN_SYSTEM` 的內容
   換成一行指標，例如 `// 順序不可調換，理由見 §7 #26`。

## 兩種不可以蒸發的內容

壓短或搬走都行，**消失不行**——這個 repo 的迴歸幾乎都是靠它們擋下來的：

- **量過的數字**（「實測 174 筆」「248.9px 單行放得下」）
- **「改了 X 會壞 Y」**

## 不要動的

`eslint-disable`、`@ts-expect-error`、`v-html` 旁的安全說明、型別與 API 的 JSDoc、
以及 `scripts/verify-all.ts` 裡 `guards` 那種**斷言在守什麼**的字串——那是功能不是說明。

## ⚠️ 改註解可能讓測試變紅

`tests/` 有六個檔用 `readFileSync` 讀原始碼做斷言。踩雷 `§7 #166`：
**字串比對的斷言會被註解餵飽。**

變紅有兩種解釋，而且長得一樣：刪掉了它真正要守的東西／**那條斷言本來就是被註解
餵成綠的**。⇒ 不要為了讓它綠而改測試，先分辨是哪一種。
